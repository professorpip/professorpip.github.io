Windows versus Ubuntu for llama.cpp on the same Ryzen PC

Project period · August-September 2026

Adding a second NVMe with Ubuntu let the same Ryzen GPU run llama.cpp from either OS off one shared model store, with dual-boot control turning out to matter more than raw speed.

  • Local AI
  • Ryzen
  • Inference
  • Hardware Reuse

In brief

  • A second NVMe drive let a Windows gaming/LLM PC dual-boot into Ubuntu without touching the existing Windows install.
  • A persistent, boot-safe NTFS mount let both operating systems share one model file store, so nothing had to be downloaded twice.
  • Once builds and quantisation matched, llama.cpp performance on the same GPU was close between Windows and Ubuntu — the practical win was safe, one-shot dual-boot control, not raw speed.
  • Ubuntu-side wake-on-LAN after shutdown stayed unreliable despite several fixes, while Windows-side WoL worked cleanly.
  • A later DDR4 memory-frequency bump helped CPU/MoE-heavy models modestly and did nothing for GPU-resident ones, showing the two boot environments still exposed genuinely different bottlenecks.

Question

The Ryzen 9 3950X / RTX 5060 Ti 16GB PC (RyzenPW) had been a Windows-only local-LLM box, using Windows llama.cpp builds against a growing Hugging Face model collection. Phil installed Ubuntu Server on a second NVMe to get a proper Linux local-LLM platform without losing the existing Windows setup or its downloaded models. The real question wasn’t “which OS is faster” in the abstract — it was whether the same GPU, the same model files, and the same day-to-day workflow could genuinely serve both operating systems, and what would actually change once that was true.

Setup

Windows 11 stayed on the original 2TB WD_BLACK SN850X NVMe, untouched. Ubuntu Server went on a separate NVMe with its own boot entry. Passwordless SSH with sudo was set up for the Ubuntu side (ryzen-ubuntu / hostname ryzehl), matching the existing Windows SSH access. The GPU driver stack (NVIDIA 595.84, CUDA 13.1) and a current ggml-org/llama.cpp CUDA/Blackwell build (sm_120a) were installed fresh on Ubuntu, requiring a small patch to CUDA 13.1’s math_functions.h for rsqrt/rsqrtf declarations under Ubuntu’s glibc.

What we tried

Boot-safe, reversible dual-boot. Rather than making Ubuntu or Windows the sole default, Tiggy set Ubuntu as the persistent default boot OS and used the UEFI BootNext mechanism for one-shot Windows boots, so a normal reboot always returns to Ubuntu without a lasting BIOS change. This kept both operating systems available without a boot-order fight every time either one was needed for a specific job.

Sharing the model store instead of duplicating it. Windows hibernation and Fast Startup were disabled (powercfg /hibernate off) so the Windows NTFS volume was always in a state safe for external read/write access. Ubuntu then got a persistent, UUID-keyed, boot-safe (nofail) mount of the Windows C: drive at /mnt/windows. This exposed the existing Windows-side GGUF collection to Ubuntu directly — the same Qwen3.8-27B-class quantisations already downloaded and tested on Windows became testable from Ubuntu’s newer CUDA/Blackwell build without another multi-gigabyte download.

A genuine like-for-like comparison. With the shared mount in place, Tiggy ran the same previously-tested Windows GGUF directly from /mnt/windows under the Ubuntu llama.cpp build, rather than a different model or a different build on each side. Historical Windows-side results and the fresh Ubuntu-side run became directly comparable for the first time, establishing the pattern for future comparisons: never re-download a model just to move operating systems.

Where the OS choice stopped mattering. Once quantisation, context size, KV-cache mode and build were held constant, the underlying llama.cpp inference numbers were close between Windows and Ubuntu on the same GPU — as expected, since both were driving the same NVIDIA CUDA stack on the same silicon. The interesting differences turned out to live elsewhere: file-system I/O and boot/power behaviour, not raw token generation.

Where it didn’t. A separate NVMe throughput test exposed a real filesystem-layer gap: the faster raw drive (WD_BLACK SN850X, ~3.61 GB/s) achieved only ~0.96 GB/s through the /mnt/windows NTFS-3G/FUSE path in a real io_uring-heavy workload, versus ~1.94 GB/s from a native Ubuntu ext4 drive doing the same job. The lesson: NTFS-3G is fine for casually sharing already-loaded model files, but is not the drive to build a serious I/O-bound Linux workload on top of.

Power and wake behaviour diverged sharply. Windows-initiated shutdown-then-wake-on-LAN worked reliably. Ubuntu-initiated shutdown-then-WoL did not, even after enabling standby power, Netplan WoL configuration, a shutdown hook, PCIe wake, disabling Energy-Efficient Ethernet, and setting the BIOS “Restore AC Power Loss” option to Power On. This remained an open, deliberately parked problem — later addressed separately with dedicated physical recovery hardware rather than a further OS-level fix.

A later, separately-tested memory tweak showed the two boot environments still have different bottlenecks. Increasing DDR4 from 2666 to 2933 MT/s (at 1.35V, DOCP) produced no measurable change for GPU-resident models like Dirk (43.16 → 43.12 tok/s), but a modest, repeatable ~5-6% generation uplift for the CPU/MoE-heavy Flash-Next Q2 profile (16.0 → 16.9 tok/s). This confirmed that “the OS doesn’t matter for speed” only held once a workload was safely inside VRAM; CPU-offloaded MoE work stayed sensitive to system memory bandwidth regardless of which OS was running it.

Result

The practical outcome was not a performance verdict but an operating model: one Ryzen PC, two operating systems, one shared model library, and a safe, reversible way to move between them without re-downloading anything or risking the working Windows install. Raw llama.cpp throughput on the GPU itself was close to identical across OSes once builds matched. The genuinely useful engineering differences were in filesystem behaviour under a cross-OS mount and in power/wake reliability, not in inference speed — and Ubuntu-side WoL remained a known, unresolved gap at the end of this stage.

What we would do next

Ubuntu-shutdown wake-on-LAN is still unsolved by OS-level configuration alone; a physical recovery path (servo button-presser plus JetKVM) was the eventual answer, covered in a later note. A further DDR4 timing pass, beyond the conservative frequency-only bump made here, was intentionally deferred pending a longer stability soak. The Windows/Ubuntu comparator itself is now reusable: any future GGUF or build change can be tested on both operating systems from the same shared model store without new downloads.
