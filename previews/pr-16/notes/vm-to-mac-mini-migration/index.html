Migrating an OpenClaw agent from a VM to a Mac mini without losing continuity

Project period · May 2026

Moving a personal assistant's identity from two aging VM instances onto a dedicated Mac mini meant deciding what continuity to keep and what stale state to leave behind.

  • Tiggy
  • OpenClaw
  • Agent Architecture
  • Reliability
  • Hardware Reuse

In brief

  • Two earlier VM-hosted instances had drifted into a confusing three-instance landscape: one worked but was messy, one was a slower stand-in.
  • A new Mac mini was set up as a dedicated, always-on, least-privilege host, with a standard non-admin macOS account running the assistant.
  • Migration was selective: memories, persona and tool notes moved; credentials, auth state, sessions, cron state and device identity did not.
  • A brief post-cutover identity glitch, the assistant answering as the wrong prior model, was caught and fixed by rewriting identity files.
  • The result established a durable host pattern reused for later projects: standard-user service account, GUI auto-login plus immediate lock, always-on power settings.

Question

An assistant running as “Tiggy” for a couple of months on a Linux VM had degraded. A git-based update attempt left it in a messy state, and a second, newer VM instance, “Tiggy2,” had been stood up as a stand-in but suffered slow-reply issues of its own. Three instances were running simultaneously with overlapping identities, on two different Ubuntu VMs and no dedicated hardware.

The question was how to consolidate onto one clean, dedicated, always-on host, a new Mac mini M4, without losing accumulated memory and personality. It also had to avoid carrying forward whatever had broken the original instance.

Setup

The Mac mini M4 connected over wired Ethernet with a DHCP reservation and a stable hostname. Two macOS accounts were created: an admin account for setup, and a separate standard non-admin account to run the assistant day to day, establishing a least-privilege split from the first install. Power settings were set for always-on operation. OpenClaw was installed under the standard account using the framework’s one-line setup script.

Both prior instances were reachable over the LAN: the original VM running an older git-based install, Tiggy2 running an npm-based install. A temporary NFS export from both VMs’ home directories gave the new Mac mini read access to their state during migration, flagged at the time for tightening or removal once migration finished.

What we tried

Verifying a clean install before touching old state. The new Mac mini’s OpenClaw install was verified independently first. That meant a running gateway, a loaded LaunchAgent, a scripted round-trip test confirming the right model was live, and the message-owner allowlist set before any old context arrived. The migration target was a known-good baseline, not an unknown quantity being modified live.

Backing up both source instances first. Both VMs were archived to compressed tarballs on the Mac mini before any selective copying began, giving a rollback point independent of the live migration script.

A narrow definition of “continuity.” The instruction was explicit: copy memories, persona, tool notes, birthdays, migration documentation and old runbooks. Do not copy openclaw.json, credentials, auth state, sessions, cron state, or device identity from either old instance. The Mac mini kept the parts of the assistant’s identity that make it feel continuous: its knowledge and voice. It discarded the state most likely to be stale, VM-specific, or responsible for the original problem. A stale bootstrap file was moved aside rather than deleted, preserved as an artefact without confusing the running assistant.

Catching an identity glitch. Shortly after cutover, the bot briefly answered as if it were the older Tiggy2 instance. IDENTITY.md and MEMORY.md were rewritten to state that the current assistant is Tiggy on the Mac mini. The original VM and Tiggy2 were logged as prior context, not parallel live identities. Tiggy2 was kept, powered down, as a continuity backup.

A durable host pattern. The choices made for the Mac mini became the standard pattern reused for later projects: a non-admin service account, GUI auto-login plus an immediate screen lock, and always-on power.

Result

The original VM instance was shut down for good. The second VM instance remained as a dormant backup, not a competing live instance. The Mac mini became the sole primary, verified end to end. OpenClaw ran at a known version, the gateway ran as a LaunchAgent, and chat delivery worked. Cron jobs were re-enabled after a local CLI scope fix, and a clean reboot test proved the auto-login/lock/gateway-start sequence survived a real restart. The one genuine failure caught during migration, the brief identity confusion, was resolved by explicit correction.

What we would do next

The broad NFS export used for migration convenience needed tightening or removal once the selective copy was complete, flagged at the time as follow-up. The least-privilege account split adopted here proved durable enough to become the default posture for later hardware.
