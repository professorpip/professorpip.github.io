The OpenClaw update that silently lost LAN access

Project period · September 2026

An OpenClaw update left a duplicate, disabled macOS Local Network permission entry for the same process, silently blocking every LAN peer and pointing suspicion at the wrong systems first.

  • OpenClaw
  • Reliability
  • Networking
  • Security

In brief

  • A routine OpenClaw version update (2026.7.1-2 to 2026.9.4) coincided with the assistant losing the ability to reach any LAN peer at all.
  • The real cause was macOS silently creating a second, disabled Local Network permission entry for the updated process, alongside the original enabled one.
  • Symptoms looked like a Home Assistant or router/firewall problem first, because the assistant could still run commands and answer chat, just not reach anything on the LAN.
  • Enabling the disabled duplicate entry in System Settings fixed live LAN access immediately, with no further changes needed.
  • The durable lesson: after any future OpenClaw update, check macOS Local Network permissions for duplicate or disabled entries before investigating the home network itself.

Question

During an OpenClaw update from 2026.7.1-2 to 2026.9.4, the assistant became unable to reach anything on the home LAN: Home Assistant, the Unraid NAS, OpenWRT access points, and other local peers all stopped responding to the live runner, even though the assistant itself was still up and could still read memory, use non-network tools, and reply in chat. The obvious suspects were the things that had recently changed or historically been flaky: Home Assistant itself, or the OPNsense router/firewall. The real question was simpler and much less obvious: had the update actually broken networking, or had something entirely outside OpenClaw quietly changed?

Setup

The host was the same Mac mini running the assistant day to day, with an OpenClaw Gateway running as a macOS LaunchAgent. The update itself completed without an error being reported, and the assistant remained reachable via Telegram, so the failure mode was specifically “the live runner cannot reach LAN peers,” not “the assistant is down.” This is an easy failure mode to misdiagnose, because everything about the assistant’s own health checks can look fine while the actual capability that matters — reaching the rest of the home network — is silently gone.

What we tried

Ruling out the obvious network-side suspects first. Before touching macOS system settings, the usual home-network health checks were run: was Home Assistant actually up, was the router doing anything unusual, had OPNsense changed. These came back clean, which is itself useful evidence — it meant the fault was very likely local to the Mac mini’s own network stack or permissions, not the network itself.

Checking macOS’s per-process Local Network permission. macOS gates outbound LAN discovery/access per process through a Local Network permission prompt and toggle in System Settings → Privacy & Security → Local Network. This is a permission model many users and operators don’t think to check because it’s easy to assume it was granted once and stays granted. Inspecting it directly showed two node entries, not one: one enabled, one disabled. The update had installed or relaunched the Node process from a path or binary identity that macOS treated as distinct enough to warrant a fresh permission entry — and that fresh entry defaulted to disabled, silently, with no prompt or error surfaced to the user or the assistant.

A one-toggle fix, once correctly diagnosed. Enabling the disabled node entry immediately restored live LAN access. No LaunchAgent restart, no OpenClaw reinstall, no network configuration change was needed — the entire fault was that one specific macOS permission toggle.

Full post-fix verification, not just “seems to work now.” Rather than accepting the fix on the strength of one successful ping, a fuller check confirmed the live runner could reach the router, the Unraid NAS, Home Assistant, and an OpenWRT access point; that HTTP requests to the Unraid management agent and Home Assistant’s REST API both returned successful responses; and that scheduled battery-monitoring scripts, which depend on reaching Home Assistant, completed cleanly and quietly rather than throwing errors.

Other issues surfaced in the same update, kept separate from the LAN root cause. The same update night also required fixing scheduled job failures caused by a changed config shape for managed environment variables (old scripts expected a flat env.HA_MCP_TOKEN; the current config nests it under env.vars.HA_MCP_TOKEN), and separately restoring Active Memory/embedding search after an OpenAI embeddings credit-balance failure by explicitly setting the embedding provider to "none". These were real, independent problems worth fixing, but treating them as one undifferentiated “the update broke everything” event would have obscured the specific, narrow, and easily fixable LAN permission cause.

Result

Live LAN access was fully restored by enabling the single disabled node entry, verified by successful reachability, HTTP 200 responses from Home Assistant and the Unraid management agent, and clean completion of LAN-dependent scheduled jobs. The update-night incident, considered as a whole, was more stressful and time-consuming than the eventual root cause deserved: verification by CLI health checks alone had not been enough, and direct intervention was needed to notice the assistant had gone unresponsive during the broader recovery. The specific LAN cause, once found, was a single toggle — the difficulty was entirely in diagnosis, not in the fix.

What we would do next

The durable operational change was explicit: future OpenClaw updates should proactively test LAN peer reachability from the live runner as a standard post-update check, and specifically inspect macOS Local Network permissions for duplicate or disabled entries before suspecting Home Assistant or the router. This is now a documented first-check rather than something to rediscover from scratch after the next update that happens to trigger the same macOS behaviour.
