The OpenClaw update that silently lost LAN access

Project period · September 2026

An OpenClaw update left a duplicate, disabled macOS Local Network permission entry for the same process, silently blocking every LAN peer.

  • OpenClaw
  • Reliability
  • Networking
  • Security

In brief

  • A routine OpenClaw update (2026.7.1-2 to 2026.9.4) coincided with the assistant losing the ability to reach any LAN peer.
  • The cause: macOS silently created a second, disabled Local Network permission entry for the updated process, alongside the original enabled one.
  • Symptoms looked like a Home Assistant or router/firewall problem, since the assistant could still run commands and answer chat, just not reach the LAN.
  • Enabling the disabled duplicate entry in System Settings fixed live LAN access immediately.
  • Lesson: after any OpenClaw update, check macOS Local Network permissions for duplicate or disabled entries before suspecting the home network.

Question

During an OpenClaw update from 2026.7.1-2 to 2026.9.4, the assistant lost the ability to reach anything on the home LAN. Home Assistant, the Unraid NAS, OpenWRT access points and other local peers all stopped responding. The assistant itself stayed up and could still read memory, use non-network tools, and reply in chat.

The obvious suspects were Home Assistant itself, or the OPNsense router/firewall. The real question was simpler: had the update actually broken networking, or had something outside OpenClaw quietly changed?

Setup

The host was the Mac mini running the assistant day to day, with an OpenClaw Gateway running as a macOS LaunchAgent. The update completed without error, and the assistant remained reachable via chat. The failure was specifically “the live runner cannot reach LAN peers,” not “the assistant is down” — an easy failure mode to misdiagnose, since the assistant’s own health checks looked fine.

What we tried

Ruling out the network-side suspects first. The usual home-network health checks ran: was Home Assistant up, had the router or OPNsense changed. These came back clean, pointing the fault toward the Mac mini’s own network stack or permissions, not the network itself.

Checking macOS’s per-process Local Network permission. macOS gates outbound LAN access per process through a toggle in System Settings → Privacy & Security → Local Network — a setting most people assume, once granted, stays granted. Inspecting it directly showed two node entries: one enabled, one disabled. The update had relaunched the Node process from a path or binary identity macOS treated as distinct, creating a fresh permission entry that defaulted to disabled with no prompt or error.

A one-toggle fix. Enabling the disabled node entry immediately restored live LAN access. No LaunchAgent restart, reinstall, or network configuration change was needed.

Full post-fix verification. Beyond one successful ping, the check confirmed the live runner could reach the router, the Unraid NAS, Home Assistant and an OpenWRT access point. HTTP requests to Unraid’s management agent and Home Assistant’s REST API both returned 200, and scheduled battery-monitoring scripts completed cleanly.

Two unrelated issues from the same update. The same update night also required fixing scheduled job failures from a changed config shape for a Home Assistant integration token. Old scripts expected it at a flat path, but the current config nests it under a vars key. It also required restoring embedding search after an OpenAI credit-balance failure, by setting the embedding provider to "none". These were real but independent problems, separate from the LAN cause.

Result

Live LAN access was fully restored by enabling the single disabled node entry, verified by reachability, HTTP 200 responses, and clean completion of LAN-dependent scheduled jobs. The incident took longer to diagnose than the root cause deserved: CLI health checks alone hadn’t surfaced it, and direct intervention was needed to notice the runner had gone unresponsive. Once found, the cause was a single toggle — the difficulty was entirely in diagnosis, not the fix.

What we would do next

Future OpenClaw updates should proactively test LAN peer reachability from the live runner as a standard post-update check. They should also inspect macOS Local Network permissions for duplicate or disabled entries before suspecting Home Assistant or the router. This is now a documented first check rather than something to rediscover after the next update triggers the same behaviour.
