Running Hermes Agent in an isolated Ubuntu VM

Project period · June–September 2026

How a disposable Ubuntu VM became a useful local-agent worker without becoming another household administrator.

  • Agent Architecture
  • Local AI
  • Hermes
  • Home Lab

In brief

  • We installed Hermes on a small Ubuntu VM instead of the automation host.
  • The VM used a local OpenAI-compatible model endpoint and a restartable system service.
  • Telegram access was allowlisted and mention-gated.
  • Useful jobs arrived gradually: research triage, platform watching, date lookahead and benchmark work.
  • Isolation made experimentation cheap; permissions kept the worker subordinate.

Hermes Agent is an open-source agent runtime that can call tools and carry out multi-step work around a language model. We wanted to know whether it could serve as a local worker beneath a supervising OpenClaw agent, without inheriting access to the rest of the home lab. An isolated Ubuntu VM gave that question a safe place to fail.

Installation context: the worker VM has 4 virtual CPUs and 8 GB RAM and runs Ubuntu Server 26.04 LTS. The experiment began with Hermes 0.16.0 in June 2026; by this September review the maintained installation reported Hermes Agent 0.18.0. Model endpoints and messaging credentials remain outside the public configuration.

Build the smallest useful host

The base was an Ubuntu Server VM with passwordless administration for maintenance, but no broad access to household systems. Hermes installed under one unprivileged user. Its gateway ran as a systemd service, so process supervision and boot behaviour were explicit rather than hidden in a terminal session.

The first model path used Hermes’ existing OpenAI-compatible provider support. Later tests pointed it at a quantised Qwen endpoint on the Ryzen GPU. A tiny exact-response smoke test proved the full CLI path before messaging was added.

Telegram was treated as an ingress adapter, not authority. One user was allowlisted; group chats required a mention; tokens stayed in the VM’s private environment file. When a later evaluation cleanup accidentally removed the live environment, restoring only the Telegram variables was safer than copying an old configuration wholesale.

Add bounded jobs gradually

The first useful tasks were read-heavy and bounded: review a discovered video, watch upstream projects, check annual dates and run local benchmark exercises. Each had a narrow wrapper, durable output and an obvious failure state.

That shape mattered. Hermes could create a workbook after consulting local documentation and could produce useful finance artefacts. It also missed exact filenames, repeated work and occasionally exhausted context. The VM boundary limited the blast radius while those behaviours were measured.

An experimental agent broker later made the hierarchy explicit: Phil remained principal, Tiggy the supervising coordinator and Hermes a worker. Default permissions excluded destructive actions, direct messages, external writes and home-infrastructure control. Worker requests were proposals, never commands.

Result

The VM turned Hermes into a practical laboratory: persistent enough to acquire jobs, disposable enough to repair, and constrained enough that a surprising model response was an evaluation result rather than a household incident.

The installation lesson was not a clever command. Put an experimental agent behind an operating-system boundary, prove one path at a time, and expand its authority more slowly than its capabilities.
