Layered physical recovery with a servo button-presser and JetKVM

Project period · July-August 2026

When software wake mechanisms couldn't reliably bring a PC back after shutdown, two independent hardware layers, a servo pressing the physical power button and a JetKVM giving full remote screen/keyboard/mouse, filled the gap without adding a single point of failure.

  • Hardware Reuse
  • Reliability
  • Home Lab
  • Automation

In brief

  • Wake-on-LAN worked reliably from a Windows shutdown but stayed stubbornly unreliable from an Ubuntu shutdown on the same PC, despite several genuine fixes.
  • A simple Arduino-plus-micro-servo rig, clamped over a laptop’s physical power button, gave a software-independent way to turn a machine on regardless of its OS or network state.
  • A separate JetKVM device gave full remote screen, keyboard, mouse and even BIOS access, letting recovery continue past the power-on moment into actually diagnosing and fixing a stuck boot.
  • Getting the servo to work reliably needed real hardware debugging, capacitor filtering, serial-port double-open bugs, and manual angle tuning, not just “wire it up and it works.”
  • The two layers are deliberately independent: JetKVM’s own power controls are treated as unused/unapproved by default, so the servo remains a working fallback even if JetKVM’s own automation permissions are restricted.

Question

Modern remote-recovery options — wake-on-LAN, remote power management, cloud-based out-of-band tools — all assume something on the machine or network is still cooperating. What happens when a home-lab PC is simply off, or locked in a state where none of the software wake paths work? Two related problems on the same Ryzen PC made this concrete: Ubuntu-initiated shutdown left wake-on-LAN unreliable even after fixing standby power, Netplan WoL configuration, PCIe wake settings, disabling Energy-Efficient Ethernet, and setting the BIOS “Restore AC Power Loss” option to Power On. If all of that still didn’t guarantee a wake, the real fix needed to not depend on the OS being cooperative at all — a genuinely physical path to pressing the power button.

Setup

The initial build target was a laptop, using an ATmega168-based Arduino board connected over FTDI USB serial, driving a small SG90 micro-servo through a signal pin on an expansion shield. A separate, unrelated device, a JetKVM IP-KVM unit, was already deployed on the LAN for another PC needing full remote screen/keyboard/mouse access, including into BIOS.

What we tried

Building the simplest possible physical actuator. Rather than anything elaborate, the design was a servo horn clamped to physically press a laptop’s power button on command, controlled over serial from a simple sketch listening for single-character commands (P for press, R/U for rest, D for hold-down, T for a test double-press).

Real hardware debugging, not just wiring. The servo initially jittered and caused what looked like intermittent resets; adding a 1000µF capacitor across the servo’s 5V/GND rails smoothed this out completely, confirmed by a clean continuous-sweep test before returning to the actual button-press sketch. A first attempted press command appeared to succeed (the control script reported success) but produced no physical movement; diagnosis, using a bare Python pyserial session to watch the raw serial exchange, found the Arduino did print READY, receive P, and reply PRESS — proving the command path worked — but the higher-level shell script was opening the serial port twice (once via stty, once via redirection), causing a reset right as the command was sent. The actual fix needed two iterations: first keeping one file descriptor open throughout, then discovering the port was still being closed too quickly after sending, interrupting the servo mid-motion; the working fix held the port open for several seconds after each command depending on which command was sent.

Mechanical tuning as a distinct, separate problem from the electronics. Even once command delivery was proven reliable, the physical press direction was initially backwards — moving away from the button rather than into it — and had to be corrected by swapping which angle counted as rest versus press. Getting a reliable physical press then took iterative small adjustments to the exact press angle and to the physical mounting position of the servo horn, with the button only reliably triggering once both the software angle and the hardware mounting were dialled in together; success was ultimately confirmed by watching the target machine actually begin booting.

Making the tool discoverable without a special vocabulary. Because the finished tool was useful but easy to misidentify later (it initially got looked up as if it might be a Home Assistant entity), it was documented plainly as the servo button-presser going forward, with a durable reminder to also mention JetKVM’s presence whenever the servo button-presser is invoked, since the two tools are complementary.

Extending the same tool to a second target. When wake-on-LAN proved unreliable specifically for the Ubuntu-side shutdown of a different PC, the same servo-button-presser concept was identified as a candidate physical recovery option for that machine too, alongside JetKVM’s own power controls and a deeper BIOS/OS wake-setting audit — explicitly kept as parked options rather than force-fitted immediately, since the priority was proving the concept once, not deploying it everywhere at once.

Deliberately layered, not merged, safety boundaries. JetKVM itself exposes keyboard, mouse, virtual-media, power, USB-emulation, reboot and wake-on-LAN tools through its own automation interface, but power/reboot/WoL-class actions were explicitly scoped as not-yet-approved for automated use, with only screenshot/read-only access approved by default. This kept the servo button-presser as a genuinely independent recovery layer: even if JetKVM’s own power automation were restricted or malfunctioning, physical power-on didn’t depend on it, and once a machine was powered on, JetKVM still provided the full remote screen/keyboard/mouse access needed to actually see what was happening and intervene, including reaching BIOS setup directly when needed.

Result

The servo button-presser reliably powered on its original laptop target on command, proven by watching it actually begin booting after a single press command, with the full serial command path (single held-open connection, correct hold timing per command, corrected press angle and horn position) verified working end to end. JetKVM was separately proven for BIOS-level access on the Ryzen PC, used to inspect and adjust real BIOS settings (including the AC-power-restore setting relevant to wake reliability) without a keyboard/monitor physically attached to that machine. Together, the two tools gave a working answer to “the PC won’t come back and nothing software-based is helping”: press the button physically first, then take full remote control once it’s powered on.

What we would do next

The most direct follow-up is adapting the proven servo mechanism to the Ryzen PC specifically, since its Ubuntu-shutdown WoL problem was the concrete trigger for treating physical recovery as a real requirement rather than a novelty project. A second is deciding, deliberately rather than by default, whether JetKVM’s own power/reboot/WoL automation should ever be approved for unattended use, given that the servo already provides an independent, lower-privilege path to the same physical outcome.
