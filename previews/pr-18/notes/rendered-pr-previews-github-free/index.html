Rendered pull-request previews on GitHub Free

Project period · September 2026

A private repository can't enable GitHub Pages on GitHub Free, so a separate public generated-site repository became the deploy target for both production and unlisted, noindexed PR previews.

  • Github
  • Publishing
  • Eleventy
  • Automation

In brief

  • The goal was simple: draft articles privately, review rendered pull requests from a phone, and publish with one action — all for free.
  • GitHub Pages cannot be enabled on a private repository under GitHub Free, which initially looked like a dead end.
  • The fix was architectural, not a paid upgrade: keep the article source private, and let CI publish generated HTML to a second, public, otherwise-empty repository that Pages happily serves.
  • Every pull request gets its own unlisted, noindex, path-prefixed preview under that public repo, automatically posted back as a PR comment and automatically deleted when the PR closes.
  • Verification treats “the workflow succeeded” and “the public page is actually live and correct” as two different claims, because GitHub’s own Pages deployment layer can lag behind a green Actions run.

Question

The publishing goal was specific: draft lab-notebook articles privately, let a human review each one as a properly rendered web page — not a raw diff — from a phone, and publish with a single explicit action, all without paying for hosting. GitHub Pages is the obvious free static-hosting mechanism, and GitHub Actions is the obvious free CI. The blocker was that GitHub Free doesn’t allow Pages to be enabled on a private repository, and the article source needed to stay private until explicitly published. The question was whether a genuinely free architecture could still deliver rendered, reviewable previews without either exposing the source repository or paying for a plan upgrade.

Setup

The article source is an Eleventy static-site project living in a private GitHub repository. An entirely separate, otherwise-empty public repository was created purely as a Pages deployment target. GitHub Actions in the private repository builds the site and, depending on the trigger, either publishes it to the public repository’s production root or to a per-pull-request preview path.

What we tried

Splitting “source of truth” from “hosting target.” Rather than trying to work around GitHub Free’s Pages restriction directly, the architecture simply stopped needing Pages on the private repository at all. The private repo holds the article Markdown, front matter, diagrams and build tooling; the public repo holds nothing but generated HTML, pushed there by CI. A scoped deploy key, stored as a repository secret in the private repo, gives the publish workflow just enough access to push to the public repo’s Pages branch, without exposing the private repo’s own contents.

Making every pull request a rendered preview automatically. The CI workflow branches on trigger type: a push to main builds with production settings and publishes to the public repo’s root; a pull-request event builds with SITE_PREVIEW=true and a per-PR base path (/previews/pr-N/), publishes to that specific unlisted subpath, and posts the resulting preview URL back as a comment on the PR itself. Preview pages carry a noindex meta tag so they’re technically public but not meant to be found or indexed. Closing the PR triggers a cleanup job that removes that PR’s preview subtree entirely, so stale previews don’t accumulate indefinitely on the public host.

Treating a green CI check as necessary, not sufficient. GitHub Actions reporting a successful workflow run doesn’t, by itself, prove the public page is live and correct — GitHub Pages deployment is a separate layer that can genuinely lag behind a green Actions run, and a build can succeed while still containing stale or incorrect content if a step was misconfigured. The verification discipline settled on was to always independently fetch the actual production URL, article URL, and any relevant image assets after a publish, and separately fetch the actual preview URL after a PR update — checking real HTTP status codes and real page content, not just trusting the Actions log. This caught real problems in practice: on one early PR, newly added image assets initially returned a stale cached 404 immediately after deployment and needed a second, deliberate fetch to confirm they’d actually landed.

Proving the full loop before trusting it. The very first real article PR was used specifically to validate the entire draft → phone-reviewable preview → merge → publish path end to end, rather than assuming the pieces would compose correctly just because each individually worked. Both the production Action and the separate public Pages deployment were independently confirmed to succeed, and the live article was fetched and read at its real public URL before the workflow was trusted for routine use.

Building in intentional friction against accidental exposure. Because the whole point was previewing without publishing, unrelated safety properties were treated as first-class requirements alongside “does the preview render”: confirming a closed PR’s preview path returns a real 404 rather than lingering, confirming production genuinely omits anything still marked as a draft, and confirming an editorial-backlog page meant to be preview-only is absent from the production build entirely. These became routine parts of verifying any PR, not a one-off check done only when the system was first built.

Result

The finished system let articles be drafted entirely in a private repository, reviewed as fully rendered, mobile-friendly web pages via automatically generated and automatically commented PR preview links, and published with one explicit merge action — all on GitHub Free, with no paid plan and no exposure of the private source repository’s contents. The split-repository pattern (private source, public generated output, scoped deploy key) turned out to be the entire solution to what initially looked like a hosting-tier limitation.

What we would do next

The pattern generalises beyond this one notebook: any other private-source, public-output publishing project facing the same GitHub Free Pages restriction can reuse the identical split-repository-plus-scoped-deploy-key architecture without modification. The remaining operational discipline worth carrying forward is the verification habit itself — always independently fetching real URLs after a workflow reports success, rather than trusting a green check alone, since the two things this project cared about (CI succeeded, and the public page is actually correct) are genuinely separate claims that can diverge.
