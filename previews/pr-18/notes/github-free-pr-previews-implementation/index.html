Implementing GitHub Free PR previews for a private-source, public-output site

Project period · September 2026

A concrete recipe for path-prefixed, noindex PR previews on GitHub Free, plus the cache and propagation pitfalls a green Actions check won't catch.

Question

Building an approval-gated lab notebook with GitHub Actions explains why this project splits private source from public output on GitHub Free. This note is the configuration recipe: how every pull request gets its own working, path-prefixed, noindex preview. It also covers the pitfalls that only surface once you verify a preview is actually live and correct.

Setup

The CI workflow sets two environment variables depending on trigger type: SITE_PREVIEW, a boolean flag, and SITE_BASE_PATH, a path prefix such as /previews/pr-17. A push to main sets neither, producing root-relative production output. A pull-request event sets both, so the build assumes it will be served from a numbered preview subpath on the public repository.

What we tried

A base-path/preview-flag recipe. Every template and asset reference resolves through a withBase() helper that prefixes SITE_BASE_PATH when set. The same Nunjucks templates and Markdown produce correct root-relative links in production and /previews/pr-N/-relative links in preview, with no per-environment branching. The same SITE_PREVIEW flag also switches in the robots meta tag and gates whether the preview-only editorial backlog renders.

Treating the path prefix as a real test. Building under /previews/pr-N/ rather than root catches bugs a local npm run serve never would. An absolute /assets/... reference might resolve locally but break under a subpath. The project’s link checker runs against both production and preview builds for this reason.

Two pitfalls only real-URL verification catches. A green Actions run doesn’t prove the public page is live. GitHub Pages deployment is a separate layer that can lag a successful build by tens of seconds. Separately, a CDN edge cache can serve a stale 404 for a newly added asset even after the file is genuinely present. A second fetch, or a cache-busting query string, confirms the asset actually landed.

Cleanup as a distinct check. Closing a PR triggers a job that removes its preview subtree from the public repository. Confirming this worked means fetching the old /previews/pr-N/ path afterwards and checking for a real 404, not just reading the cleanup job’s own success status.

Result

The base-path/preview-flag recipe, combined with independent HTTP verification of both preview and cleanup paths, gives a repeatable per-PR preview with no manual steps beyond opening the pull request. Pages deployment lag and CDN cache staleness are now checked on every PR update as routine, not treated as surprises.

What we would do next

The base-path/preview-flag pattern generalises to any Eleventy, or similarly template-driven, static site facing the same GitHub Free restriction. The habit worth carrying forward is simple: always fetch the real preview and cleanup URLs independently, rather than trusting a green check alone.
