Implementing GitHub Free PR previews for a private-source, public-output site

Project period · September 2026

A concrete recipe for path-prefixed, noindex PR previews on GitHub Free — base-path plumbing, cleanup, and the cache/propagation pitfalls that a green Actions check alone won't catch.

In brief

  • The GitHub Free / private-source-public-output split-repository pattern is described in Building an approval-gated lab notebook with GitHub Actions; this note is the practical implementation companion, not a repeat of that architecture story.
  • The concrete recipe: an Eleventy SITE_BASE_PATH/SITE_PREVIEW environment pair drives both the build’s asset paths and a <meta name="robots" content="noindex, nofollow"> tag, so the same codebase produces production or any numbered preview from one build command.
  • A path-prefixed preview is a genuinely different test than a root-only local build: it catches absolute-path asset and internal-link mistakes that a local npm run serve never exercises.
  • Two specific pitfalls repeatedly needed independent verification rather than trust in a green Actions log: GitHub Pages’ own deployment layer lagging behind a successful build, and a CDN edge cache serving a stale 404 for a newly added asset immediately after deploy.
  • Preview cleanup on PR close needs its own explicit check — confirming the old /previews/pr-N/ path returns a real 404, not just that the workflow reported success.

Question

Building an approval-gated lab notebook with GitHub Actions covers why this project uses a split private-source/public-output repository pattern on GitHub Free. This note covers the part that story doesn’t: the concrete configuration recipe for making every pull request produce its own working, path-prefixed, noindex preview — and the specific pitfalls that only show up once you try to verify a preview is actually live and correct, not just that a workflow finished.

Setup

The private repository’s Eleventy build reads two environment variables set by the CI workflow depending on trigger type: SITE_PREVIEW (a boolean flag) and SITE_BASE_PATH (a path prefix, e.g. /previews/pr-17). A push to main runs the build with neither set, producing root-relative production output. A pull-request event sets both, producing output that assumes it will be served from a numbered preview subpath on the separate public repository.

What we tried

A concrete base-path/preview-flag recipe. Every template and asset reference in the Eleventy build resolves through a small withBase() helper that prefixes SITE_BASE_PATH when set, so the same Nunjucks templates and Markdown produce correct root-relative links in production and correct /previews/pr-N/-relative links in preview, with no per-environment template branching. The same SITE_PREVIEW flag also switches in a noindex, nofollow robots meta tag and, separately, gates whether the preview-only editorial backlog renders at all.

Treating the path prefix as a real test, not a cosmetic detail. Running the build under /previews/pr-N/ rather than root-only catches classes of bug a local npm run serve never would: an absolute /assets/... reference that happens to resolve locally but breaks under a subpath, or an internal link built without the base-path helper. The project’s own link checker runs against both the production and preview builds for this reason.

Two pitfalls that only verification against the real URL catches. GitHub Actions reporting a successful workflow run doesn’t, by itself, prove the public page is live and correct — GitHub Pages deployment is a separate layer that can genuinely lag behind a green Actions run, sometimes by tens of seconds. Separately, a CDN edge cache can serve a stale cached 404 for a newly added asset immediately after deployment, even once the underlying file is genuinely present; a second, deliberate fetch (or a cache-busting query string) is needed to confirm the asset actually landed, rather than trusting the first response.

Cleanup verification as a distinct check. Closing a PR triggers a cleanup job that removes that PR’s preview subtree from the public repository. Confirming this worked means fetching the old /previews/pr-N/ path afterwards and checking for a genuine 404, not just reading the cleanup job’s own success status — the same two-different-claims discipline that applies to publishing a fresh preview also applies to removing an old one.

Result

The base-path/preview-flag recipe, combined with independent HTTP verification of both the preview and cleanup paths, produces a repeatable per-PR preview that needs no manual steps beyond opening the pull request. The specific pitfalls — Pages deployment lag and CDN cache staleness — are routine enough that they’re now checked on every PR update as a matter of course, not treated as one-off surprises.

What we would do next

The base-path/preview-flag pattern generalises directly to any other Eleventy (or similarly template-driven) static site facing the same GitHub Free Pages restriction. The verification habit — always independently fetching the real preview and cleanup URLs rather than trusting a green check alone — is the part worth carrying into any future publishing pipeline, regardless of static-site generator.
