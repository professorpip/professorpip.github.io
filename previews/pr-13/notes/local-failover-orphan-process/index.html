Local-model failover and the orphan-process bug

Project period · September 2026

A real watchdog restart proved the fallback chain—and stranded the emergency model it had launched.

  • Automation
  • Reliability
  • Local AI
  • OpenClaw

In brief

  • The Mac emergency model started in under 0.8 seconds and handled a simulated Ryzen outage.
  • An external watchdog then killed and replaced the Gateway during the model’s idle window.
  • The emergency llama-server became an orphan and missed its normal ten-minute shutdown.
  • A separate reaper now requires exact identity, healthy replacement, no client and two matching observations before sending TERM.
  • Recovery tests must inspect resource lifecycle, not only whether requests succeed.

OpenClaw’s Gateway is the long-running process that owns the agent session, provider connections and supervised local-model child processes. The normal local path used a wake-on-demand Ryzen GPU server; a smaller llama.cpp model on the Mac mini was the emergency fallback. The failover test looked successful: the Ryzen endpoint was unavailable, the Mac model started, and a response came back. Then an external watchdog replaced the Gateway—and exposed a second failure.

Proving the happy path

The emergency Qwen server had its own provider, port and 600-second idle timer. Two cold starts reached readiness in about 0.76 seconds. With the Ryzen path forced to miss its three-second deadline, the Mac fallback became ready in 1.27 seconds and returned HTTP 200 in 1.31 seconds.

The full answer still took 55.7 seconds because a small model had to process the complete agent prompt. Detection was fast; degraded inference was slow. That was acceptable for emergency use.

The failure behind the success

We then paused the Gateway while its emergency child remained inside the idle window. The external watchdog replaced the Gateway, restoring service and Telegram. The old model process lost its parent and became adopted by PID 1. Its idle owner no longer existed, so the expected shutdown never arrived.

Port health alone would have missed this. The new Gateway worked; the abandoned process still held memory.

Conservative cleanup for orphaned model processes

The repair runs outside the Gateway every 15 seconds. It matches the exact binary, dedicated port, model alias and model file. It proceeds only when there is exactly one listener, the replacement Gateway is healthy, that Gateway is absent from the model’s ancestry, no client is connected, and the same model/Gateway pair appears twice. It sends TERM, rechecks, and reserves KILL for the unchanged exact process.

In the controlled orphan test, the model became PPID 1. The reaper observed it, confirmed it on the next pass, sent TERM, and saw it exit one second later. In the normal test it ignored the Gateway-owned model, which stopped on its existing idle timer. A fresh cold start then succeeded.

Result

The fallback chain, watchdog and reaper now cover three different concerns: degraded service, control-plane recovery and resource cleanup. Combining them into one optimistic health check would hide exactly the fault the exercise found.

A resilience test is not finished when the reply arrives. Verify the old processes died, the scarce resources were released, and the next cold start still works.
