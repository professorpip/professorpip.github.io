Rooting an Astro Slide without losing the recovery path

Project period · 19–20 November 2026

A rooted Astro became a safe kernel test platform only after we separated bootloader transport, kernel execution and exact rollback.

  • Android
  • Linux
  • Astro Slide
  • Rooting

In brief

  • The goal was not merely to root an Astro Slide, but to make it a recoverable kernel-development target.
  • Bootloader unlocking erased the handset, so we captured exact firmware, slot and boot-partition evidence before experimenting.
  • The bootloader accepted fastboot boot images but failed before executing them.
  • A byte-identical stock control reproduced the failure, clearing the custom kernel of blame.
  • Controlled writes to the active boot partition became safer than a misleading one-shot path because every run included an exact restore gate.

The real question

The Astro Slide is an unusual Android device: a physical keyboard, MediaTek platform and desktop-like ambitions in a pocketable form. We wanted to turn one into an OpenWrt LTE router. That eventually required a custom kernel, which made the first question less glamorous but more important: could we modify the phone and still recover it predictably?

The handset ran Android 11 V07b on an MT6873 platform with a 4.14.186 kernel. Its bootloader was unlocked, which triggered the expected factory reset, and the exact V07b boot image was patched on the device with Magisk. Root was then verified as UID 0 in Magisk’s SELinux domain.

That result was useful, but “root works” is not a recovery plan.

Capture the device, not the folklore

Before changing the kernel, we recorded the active slot, boot partition sizes, Android build and verified-boot state. We also captured and hashed the device’s own boot-related partitions.

Those private images are deliberately not published. A boot image must match the reader’s exact firmware, and redistributing vendor material would create both safety and licensing problems.

The phone exposed two fastboot environments. Android’s adb reboot fastboot entered userspace fastbootd. Classic MediaTek LK fastboot was reached through adb reboot bootloader or the hardware-key route.

Both reported an unlocked handset, active slot A and 40 MiB boot partitions.

We did not turn slot B into a spare Linux playground. The device uses Virtual A/B update machinery, so treating the inactive slot as disposable could damage Android’s own recovery and update path.

The reusable procedure is simple:

  1. record the exact build and active slot;
  2. preserve the original images and hashes;
  3. prove physical access to classic fastboot;
  4. change only the intended partition; and
  5. verify Android, root and hardware before advancing.

The one-shot boot trap

Temporary booting looked like the perfect safety tool. LK contained a cmd_boot implementation, accepted the complete image and printed a successful-looking handoff. USB then disappeared and Android returned with boot reason lk_crash.

It would have been easy to blame the custom kernel. Instead, we repeated the experiment with a byte-identical stock control. It failed in exactly the same place.

That control changed the diagnosis. Neither image had reached the candidate-kernel execution gate; the bootloader’s temporary-boot handoff was broken. A terminal saying “Booting” proved only that the transport accepted an image.

Once the one-shot path was ruled out, a controlled persistent write became the evidence-led option. Each test wrote the candidate to the literal active boot partition, checked runtime behaviour, and restored the exact original image when the gate failed or the experiment ended. The hardware fastboot route remained available throughout.

Result

The Astro became a credible development target because recovery was treated as a layered system rather than a magic command. We separated:

  • bootloader transport;
  • candidate-kernel execution;
  • Android runtime health;
  • vendor-module compatibility; and
  • byte-for-byte restoration.

That discipline paid off repeatedly. Later kernel failures could be attributed to configuration or runtime behaviour instead of an ambiguous boot path, and the phone always returned to a known image.

The larger lesson is that a control can be more valuable than another tweak. The stock-image control prevented us from “fixing” a kernel that had never run.

What came next

With root and rollback proved, the project could tackle the actual blocker: Droidspaces needed IPC namespaces, but the shipped kernel did not provide them. The next part follows the ABI-safe kernel reconstruction and the one-line namespace fix that finally passed at runtime.
