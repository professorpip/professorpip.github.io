Building a low-cost Frigate camera estate with Thingino

Project period · July 2026

A growing mix of cheap open-firmware Thingino cameras and consumer Tapo/Reolink units under one Frigate instance stayed affordable, until a wasteful transcode setting quietly maxed out the host CPU.

  • Frigate
  • Cameras
  • Home Lab
  • Home Assistant

In brief

  • A camera estate grew organically from a handful of cheap Thingino-firmware cameras to fourteen mixed cameras under one Frigate instance, without a big-vendor subscription.
  • A near-identical config pattern for each Thingino camera (go2rtc streams, ONVIF host, detect/record roles) made adding new units mostly mechanical, backed up and restored through Frigate’s own config API.
  • A CPU-maxing incident on the NVR host wasn’t fixed by closing the live-preview browser tab; the real cause was six cameras silently forced through software libx264 transcoding instead of direct RTSP.
  • Frigate’s own pan/tilt arrow controls worked for both PTZ-capable Thingino units and a motorized Tapo TC70, making a separate Home Assistant ONVIF integration optional rather than required.
  • A live single-client serial-style resource (the Zigbee coordinator bridge) taught a separate but related lesson: don’t casually probe a shared bus you also depend on.

Question

Consumer NVR subscriptions and proprietary camera ecosystems are expensive and lock you into a vendor’s app. The alternative attempted here was to combine Frigate — a self-hosted, Coral-accelerated open-source NVR — with a growing mix of genuinely cheap cameras: Cinnado/Thingino D1-chipset units running open replacement firmware, plus a handful of consumer Tapo and Reolink cameras already in use around the house. The practical question across several months was whether this mixed, incrementally-grown estate could stay reliable and affordable as it scaled from a handful of cameras to over a dozen, without either a big recurring subscription or constant manual firefighting.

Setup

Frigate ran on the Unraid server (nec2u), backed by a Coral USB accelerator for object detection, with the camera estate accessed through Frigate’s own live config-save-and-restart API (POST /api/config/save?save_option=restart). Cameras fell into three families: Cinnado/Thingino PTZ units (identified over the LAN by their thingino HTTP title and RTSP port 554), fixed and motorized Tapo units (TC60/TC70/C520WS, identified via ONVIF port 2020), and a Reolink PoE doorbell. Each camera got a go2rtc main/sub stream pair, detection running from the lighter substream and recording from the full main stream, plus camera-group membership for the dashboard.

What we tried

A repeatable per-camera onboarding pattern. Adding a new Thingino camera became close to mechanical: light-scan the expected IP range for the device’s mDNS name and open ports, back up the live Frigate config (both raw and decoded YAML) before any change, generate a candidate config mirroring the existing Thingino pattern (go2rtc raw and ffmpeg-wrapped streams, ONVIF host, detect/record roles, camera-group membership), apply it through the API, then verify: config lists the new camera, the latest-snapshot endpoint returns a real JPEG, and camera/detection FPS settle at the expected rate. This pattern, repeated for each new camera as they were brought online through the estate’s growth, kept onboarding low-risk because every change had a config diff, a backup, and a positive functional check rather than “it looks fine in the preview.”

Discovering PTZ control was already solved. A new Tapo TC70 with motorized pan/tilt initially suggested a need for Home Assistant’s native ONVIF integration to get dashboard PTZ buttons. It turned out Frigate’s own live-view arrow controls already drove pan/tilt on both the new TC70 and the existing Thingino PTZ units, without any extra integration. HA ONVIF stayed an optional dashboard-convenience layer rather than the assumed primary control path — a case where the simpler existing tool already did the job the more elaborate plan assumed was necessary.

A CPU incident that looked like a browser problem and wasn’t. As the estate grew, the host running Frigate started showing sustained high CPU (98-100%) and elevated temperature while cameras were being previewed remotely. Closing the live-preview browser page reduced the number of skipped frames but the underlying CPU load didn’t recover. A Frigate-internal restart didn’t fix it either. The real cause, found by inspecting go2rtc’s stream configuration rather than the browser or Frigate process itself, was that six of the Thingino cameras’ main/sub stream aliases were routed through ffmpeg:...#video=h264, forcing continuous software libx264 transcoding for streams that didn’t need it, instead of connecting to the cameras’ native RTSP output directly.

A conservative, verified fix. The same backup-candidate-apply-verify pattern used for onboarding was applied to the fix itself: back up the live config, generate a candidate switching those six cameras’ main/sub aliases from the forced-ffmpeg form to direct RTSP (leaving the lower-bandwidth iOS/two-way-audio aliases untouched), apply through the config API, and verify. Forced ffmpeg hits on those streams dropped to zero, go2rtc producers became direct RTSP connections, overall Docker CPU fell from roughly 98-100% to about 50%, the Frigate container’s own CPU dropped to about 38%, and host temperature fell from the mid-90s°C to about 85°C shortly after restart.

A separate, adjacent lesson about shared serial resources. During the same broader period, the home’s Zigbee coordinator was reached over a network serial bridge (ser2net) shared with Home Assistant’s live ZHA connection. A routine TCP reachability probe against that bridge briefly knocked all Zigbee devices offline for about eight seconds before HA reconnected automatically. The practical rule that came out of it — treat a live single-client serial-style bridge as fragile to casual probing, and prefer reading through the application (HA) rather than poking the transport directly — generalised well beyond Zigbee to any shared serial/RS-485-style link in the home-lab estate, including the inverter telemetry bridge described separately.

Result

By the point covered here, fourteen cameras spanning Thingino, Tapo and Reolink hardware ran under one Frigate instance at roughly 5 fps camera/process/detection rate each, with Coral inference typically single-digit milliseconds. The CPU incident was fully resolved by the direct-RTSP fix, with no further recurrence of the forced-transcode pattern once the remaining Thingino main/sub aliases were corrected. Retention was later tuned deliberately (continuous 1→2 days, motion 3→6 days) after confirming ample headroom on the media share, rather than left at defaults or increased blindly.

What we would do next

The onboarding pattern proven here — light network scan, config backup, candidate diff, API apply, functional verification — is reusable for any future camera addition without needing to reinvent the process. The shared-serial-bus lesson from the Zigbee incident is worth applying proactively to any other RS-485/serial bridge in the home-lab estate before it causes an unplanned outage, rather than discovering it reactively again.
