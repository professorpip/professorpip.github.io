Diagnosing a misleading SunSynk battery SOC reading with local and pack-level evidence

Project period · August 2026

When a SunSynk hybrid inverter's reported battery SOC froze at an implausible value, cloud history, a local Modbus path and pack-level BMS evidence together showed the reading itself was untrustworthy.

  • Energy
  • Home Assistant
  • Modbus
  • Monitoring
  • Hardware Reuse

In brief

  • A SunSynk hybrid inverter’s cloud app reported a static ~90% battery SOC while charge/discharge cycling had effectively stopped.
  • Home Assistant’s recorder history didn’t go back far enough to date the fault; SunSynk’s own cloud energy chart did.
  • An existing local RS-485-to-Modbus-TCP bridge gave a second, cloud-independent read on the inverter.
  • Pack-level BMS telemetry from all four battery packs showed one pack diverging sharply from the other three.
  • Reported SOC couldn’t be trusted from either path. Only pack voltage, current-sharing and cell-delta data gave a reliable signal.

Question

A hybrid SunSynk inverter charges batteries overnight on cheap tariff electricity and discharges them by day. That cycling appeared to stop, while the cloud app kept reporting a suspiciously constant ~90% state of charge.

Was this a fault in the battery, the inverter, or the BMS, or was the reported number simply wrong? The task was to diagnose a misleading SOC reading using cloud history, an existing local telemetry path, and pack-level data together, rather than trusting any single source.

Setup

The inverter is a SunSynk 3.6 kW single-phase low-voltage hybrid unit feeding a rack battery bank, normally monitored through SunSynk’s cloud app and a Home Assistant cloud integration. A local RS-485-to-Modbus-TCP bridge, already running on a Raspberry Pi 3 via mbusd, gave a second, cloud-independent read on the same inverter registers.

What we tried

Dating the fault before touching hardware. Home Assistant’s recorder history only went back a few days, not far enough to find the start of the problem. SunSynk’s cloud monthly-energy chart covered the whole period.

It showed a clear transition: normal daily cycling through early July, then an overnight SOC jump from about 20% to 90% on one specific date. After that, reported SOC froze near 90% and cycling stopped. This turned a vague “something’s wrong” into a dated incident to investigate.

Cross-checking against the local Modbus path. Reading the same SOC register locally confirmed the cloud figure wasn’t a display or sync artefact. The inverter reported the same frozen ~90% value over the local path too, ruling out a cloud-side reporting or caching bug.

Adding pack-level evidence. The local Modbus path still only reported the inverter’s own view of SOC, not the cause. Once each of the four battery packs’ BMS telemetry became visible over Bluetooth, a clearer picture emerged.

One pack’s reported state of charge diverged sharply from the other three at essentially the same pack voltage. The inverter’s reported SOC, on either path, tracked neither the healthy packs nor a physically plausible value.

Finding the problem was deeper than cloud versus local. For this pack chemistry and BMS combination, reported SOC couldn’t be trusted as a primary signal at all. Pack voltage, current-sharing between parallel packs, cell-voltage delta, and temperature had to serve as the real source of truth instead.

Result

The local Modbus path proved the fault wasn’t a cloud-reporting artefact: the inverter reported the same frozen SOC locally. Pack-level BMS evidence supplied the real diagnosis.

Cross-referencing cloud history, local telemetry and pack-level data together showed the inverter’s reported SOC was following an unreliable underlying BMS value on every path, not just the cloud one. The fix was not “trust local over cloud” but “stop trusting reported SOC from either path, and read the physical pack signals directly.”

What we would do next

The natural follow-up is a controlled, closely-watched charge test using only real electrical signals — voltage, current sharing, cell delta — to decide when to stop, never SOC alone. Treating cloud history, an existing local bridge, and pack-level telemetry as complementary evidence, rather than any one as authoritative, is the reusable pattern from this incident.
