Diagnosing a misleading SunSynk battery SOC reading with local and pack-level evidence

Project period · August 2026

When a SunSynk hybrid inverter's reported battery SOC froze at an implausible value, cloud history, a local Modbus path and pack-level BMS evidence together proved the reading itself, not just one data path, was untrustworthy.

In brief

  • A SunSynk hybrid inverter’s cloud app started reporting an implausibly static ~90% battery SOC while cloud-visible charge/discharge cycling had effectively stopped.
  • Home Assistant’s own recorder history didn’t go back far enough to confirm exactly when the fault began; SunSynk’s own cloud monthly-energy chart did, pinpointing the transition date.
  • An existing local RS-485-to-Modbus-TCP bridge gave a second, cloud-independent read on the inverter; see that note for how the bridge itself was built and proved.
  • Once four battery packs’ own BMS telemetry became independently visible, pack-level voltage, current-sharing and cell-delta evidence showed the diverging pack, not the reporting path, was the real fault.
  • The eventual lesson went further than “cloud versus local”: for this pack chemistry and BMS combination, reported SOC itself could not be trusted from either path, and physical pack signals had to be used as the real source of truth.

Question

A hybrid SunSynk inverter, charging batteries overnight on cheap tariff electricity and discharging them by day, had apparently stopped doing that useful cycling — while its cloud-facing app still reported the battery sitting at a suspiciously constant ~90% state of charge. Was this a real fault in the battery, the inverter, or the BMS, or was the reported number itself simply wrong? The practical question was how to diagnose a misleading SOC reading using every evidence source available — cloud history, an existing local telemetry path, and pack-level data — rather than trusting any single source.

Setup

The inverter is a SunSynk 3.6 kW single-phase low-voltage hybrid unit feeding a rack battery bank, normally monitored through SunSynk’s own cloud app and a Home Assistant cloud-based integration. A local RS-485-to-Modbus-TCP bridge, already built on a Raspberry Pi 3 Model B Rev 1.2 running mbusd, gave a second, cloud-independent read on the same inverter registers.

What we tried

Establishing the timeline before touching hardware. Home Assistant’s own recorder history only went back a matter of days, not far enough to see when the problem actually started. SunSynk’s own cloud monthly-energy chart, by contrast, covered the whole period and showed a clear, dateable transition: normal daily charge/discharge cycling through the first several days of July, followed by an unusual overnight SOC jump from about 20% straight to 90% on one specific date, after which cloud-reported SOC essentially froze near 90% while normal cycling stopped. This turned a vague “something’s wrong” into a specific, evidence-backed incident date to investigate further — using the cloud service’s own historical data as the timeline source, even while suspecting its live readings.

Cross-checking against the existing local Modbus path. The local RS-485-to-Modbus-TCP bridge already gave an independent, cloud-free read on the same inverter registers. Reading the same SOC register locally confirmed the cloud figure wasn’t a display or sync artefact: the inverter itself was reporting the same frozen ~90% value over the local path too, ruling out a cloud-side reporting or caching bug as the explanation.

Adding pack-level evidence, not just a second telemetry path. The local Modbus path alone still only reported the inverter’s own view of SOC, not the underlying cause. Once four individual battery packs’ own BMS telemetry became independently visible over Bluetooth (a separate but related project), a clearer picture emerged: one pack’s reported state of charge diverged sharply from the other three at essentially the same pack voltage, and the inverter’s own reported SOC, whichever path reported it, tracked neither the healthy packs nor a physically plausible value.

Discovering the real problem was deeper than cloud-vs-local. The eventual operating conclusion generalised beyond this one inverter: for this pack chemistry and BMS combination, reported SOC could not be trusted as a primary signal at all, whether read from the cloud or the local bridge, and pack voltage, current-sharing between parallel packs, cell-voltage delta, and temperature had to be used as the real source of truth instead.

Result

The local Modbus path proved the fault wasn’t a cloud-reporting artefact — the inverter itself reported the same frozen SOC locally. The real diagnostic value came from adding pack-level BMS evidence on top: cross-referencing cloud history, local telemetry and pack-level voltage/current/cell-delta data together showed the inverter’s reported SOC was following an unreliable underlying BMS value on every path, not just the cloud one. The fix wasn’t “trust local over cloud,” it was “stop trusting reported SOC from either path, and read the physical pack signals directly instead.”

What we would do next

The natural follow-up, once individual pack anomalies were visible, was a controlled, closely-watched charge test using only real electrical signals (voltage, current sharing, cell delta) to decide when to stop — never SOC alone. Combining cloud history, an existing local bridge, and pack-level telemetry as complementary evidence sources, rather than treating any one as authoritative, is the reusable diagnostic pattern from this incident.
