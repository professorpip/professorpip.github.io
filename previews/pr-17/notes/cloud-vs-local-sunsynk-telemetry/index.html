Cloud versus local inverter telemetry with a SunSynk hybrid inverter

Project period · August 2026

When a SunSynk hybrid inverter's cloud-reported battery SOC stopped making sense, a local RS-485 to Modbus TCP bridge gave an independent, trustworthy view the cloud app couldn't provide alone.

  • Energy
  • Home Assistant
  • Modbus
  • Monitoring
  • Hardware Reuse

In brief

  • A SunSynk hybrid inverter’s cloud app started reporting an implausibly static ~90% battery SOC while cloud-visible charge/discharge cycling had effectively stopped.
  • Home Assistant’s own recorder history didn’t go back far enough to confirm exactly when the fault began; SunSynk’s own cloud monthly-energy chart did, pinpointing the transition date.
  • A direct RS-485 Modbus probe of the inverter, run before any cloud/local integration existed, proved the inverter itself was alive and answering correctly on the wire.
  • A Raspberry Pi running mbusd turned that single RS-485 port into a shared Modbus TCP endpoint, letting Home Assistant read the inverter locally and continuously, independent of the cloud service.
  • The eventual practical lesson went further than “add a local path”: once battery pack telemetry was available too, reported SOC itself turned out not to be trustworthy, and voltage/current/cell-delta became the real source of truth.

Question

A hybrid SunSynk inverter, charging batteries overnight on cheap tariff electricity and discharging them by day, had apparently stopped doing that useful cycling — while its cloud-facing app still reported the battery sitting at a suspiciously constant ~90% state of charge. Was this a real fault in the battery, the inverter, or the BMS, or was it simply that the only visibility into the system was a cloud service that might itself be wrong, stale, or misleading? The practical question was whether local, direct telemetry could give an independently trustworthy answer the cloud alone couldn’t.

Setup

The inverter is a SunSynk 3.6kW single-phase hybrid unit feeding a rack battery bank, normally monitored only through SunSynk’s own cloud app and a Home Assistant cloud-based integration. A Raspberry Pi (solarpi) with a USB-to-RS-485 (CH340) adapter was available to attempt a local wired connection to the inverter’s RS-485/Modbus port, as an alternative to relying solely on the cloud path.

What we tried

Establishing the timeline before touching hardware. Home Assistant’s own recorder history only went back a matter of days, not far enough to see when the problem actually started. SunSynk’s own cloud monthly-energy chart, by contrast, covered the whole period and showed a clear, dateable transition: normal daily charge/discharge cycling through the first several days of July, followed by an unusual overnight SOC jump from about 20% straight to 90% on one specific date, after which cloud-reported SOC essentially froze near 90% while normal cycling stopped. This turned a vague “something’s wrong” into a specific, evidence-backed incident date to investigate further — using the cloud service’s own historical data as the timeline source, even while suspecting its live readings.

Proving the inverter was alive on the wire, before building any integration. Before wiring up any Modbus TCP gateway or Home Assistant integration, a passive listen on the RS-485 line at several common baud rates captured nothing — which doesn’t prove a wiring fault, since Modbus RTU devices commonly stay silent until actively polled. A follow-up active Modbus RTU read of holding register 0 at 9600 8N1, slave ID 1, got a valid, CRC-correct response. This single low-level check, done before any higher-level software existed, proved the physical RS-485 connection and wiring were correct and the inverter itself was responsive — ruling out an entire category of possible causes (bad cable, wrong polarity, dead port) before writing any integration code.

Turning one RS-485 port into a shared network resource. mbusd was built from source and installed as a systemd service on the Raspberry Pi, listening on Modbus TCP port 502 and bridging to the RS-485 adapter at 9600 8N1. This let Home Assistant (and, notably, the same port, any future local tool) reach the inverter as a normal Modbus TCP endpoint over the LAN rather than needing direct serial access, verified end to end with a register read returning the correct value through the full TCP-to-serial path.

Adding the local path alongside the cloud path, not instead of it. Home Assistant’s existing cloud-based SunSynk integration was left in place, and a local Modbus-TCP-based add-on (kellerza/sunsynk) was configured to point at the new local bridge. The dashboard was deliberately restructured to show cloud and local readings side by side rather than silently replacing one with the other — treating the comparison itself as the useful artefact, not just the eventual “winner.”

Discovering the real problem was deeper than cloud-vs-local. Once four individual battery packs’ own BMS telemetry became independently visible over Bluetooth (a separate but related project), a clearer picture emerged: one pack’s reported state of charge diverged sharply from the other three at essentially the same pack voltage, and the inverter’s own reported SOC, whichever path reported it, tracked neither the healthy packs nor a physically plausible value. The eventual operating conclusion generalised beyond this one inverter: for this pack chemistry and BMS combination, reported SOC could not be trusted as a primary signal at all, and pack voltage, current-sharing between parallel packs, cell-voltage delta, and temperature had to be used as the real source of truth instead.

Result

The local RS-485/Modbus path proved itself independently trustworthy at the wire level before any software was layered on top, and gave a continuous, cloud-independent telemetry stream once mbusd and the local Home Assistant integration were running. The cloud app’s SOC reporting was ultimately shown to be following the same underlying, unreliable BMS-reported state-of-charge value as everything else — so the real fix wasn’t “trust local over cloud,” it was “stop trusting reported SOC from either path, and read the physical pack signals directly instead.”

What we would do next

The natural follow-up, once individual pack anomalies were visible, was a controlled, closely-watched charge test using only real electrical signals (voltage, current sharing, cell delta) to decide when to stop — never SOC alone. The RS-485/Modbus TCP bridge pattern proven here for the inverter is directly reusable for any other RS-485-speaking device that later needs a local, cloud-independent Home Assistant path.
