Building a one-tap lab notebook

Project period · September 2026

How a private Markdown workshop, phone-friendly rendered previews and a separate public output repository turned one merge into a controlled publication.

  • Publishing
  • Github
  • Automation
  • Eleventy
  • Agent Architecture

The original brief sounded almost suspiciously small:

  • Tiggy should turn completed experiments into readable notes.
  • Phil should be able to review them properly on his phone.
  • Nothing should become public without an explicit human decision.
  • Once approved, publishing should take one ordinary action.
  • The result should cost nothing to host and almost nothing to maintain.

The first version met most of that brief. It was a small Eleventy site fed by Markdown, with GitHub pull requests as the review queue, a private-source/public-output split and a GitHub Action publishing after merge. What it did not yet have was the rest of the system we eventually learned we needed: rendered previews, private editorial planning, evidence rules, project-period metadata, useful diagrams and resources, or wiki-style navigation.

Six pull requests later, the notebook had become both a publication and its own tested publishing workflow.

The constraint that shaped the architecture

A conventional hosted CMS would have solved the editing problem but added accounts, updates, a database and another interface. A single public Git repository would have made free static hosting simple but exposed drafts, editorial notes and revision history. Keeping the source repository private was non-negotiable, and the chosen GitHub plan could not publish that private repository directly as the public Pages site.

The answer was two repositories with deliberately different jobs:

  1. a private source repository contains Markdown, templates, automation, draft history and the editorial backlog;
  2. a public generated-output repository contains only the HTML, CSS, images and search index that Eleventy has built for publication.

The source workflow holds a write-enabled deploy key for the output repository. The public repository does not need access back into the private one. This is a small but important security boundary: the deploy step exports a product, not the workshop that produced it.

There is still no application server or database. GitHub stores the source and review conversation, Actions performs the builds, and Pages serves static files.

The pull request became the CMS

Each article starts on its own branch under content/notes/. Tiggy reconstructs the project from preserved artefacts, uses memory or transcripts to locate evidence, checks material claims, removes private operational detail, and writes the publishable Markdown.

Before opening a pull request, Tiggy runs two clean local builds:

  • a normal production-shaped build checks that existing public content still works;
  • a prefixed preview build renders the proposed site beneath /previews/pr-N/.

Both run Eleventy, build a Pagefind search index and execute an internal link-and-image checker. Opening the pull request triggers the prefixed validation again in GitHub Actions; the preview job then rebuilds, copies only the rendered output into the public repository and comments its URL on the pull request.

Phil can follow that link in the GitHub mobile app and review the actual page rather than mentally compiling a Markdown diff. Preview pages carry noindex, nofollow, are deliberately unlisted, and are deleted when the pull request closes. They are public URLs, so sensitive material still does not belong in them; “unlisted” is useful review plumbing, not access control.

The article can say draft: false in its branch without appearing on the production site. It is publishable inside the proposal, but production still comes from main. That distinction removed an awkward class of state: readiness is visible in the proposed content, while publication remains an explicit repository event.

One merge, not automatic approval

When Phil is satisfied, he merges that exact pull request. A push to main starts the production route:

  1. check out the approved source revision;
  2. install locked Node dependencies;
  3. run the complete build and internal-link validation again;
  4. write the generated site to the public repository’s Pages branch;
  5. let the public repository’s own Pages deployment serve it.

The merge is the one tap in the title. It is not a vague standing permission for Tiggy to publish, and approval of one pull request says nothing about another. The automation makes the approved action cheap; it does not automate away the approval.

That also means success has two layers. A green build in the private repository proves the source workflow ran. Publication is complete only after the public repository’s Pages workflow succeeds and the live article, its assets and representative internal links can be fetched. The same principle applies in reverse: preview cleanup is proved by the old preview returning 404, not merely by a cleanup job claiming success.

We built it by publishing with it

The repository history records the system growing under real use rather than arriving fully formed.

Pull requests 1 and 2: prove the basic loop

The first two articles—about giving Tiggy a live voice and what Tiggy is—used ordinary pull-request review. Merging each one successfully built the private source and published the generated site. That proved the central idea: a phone review followed by one merge could be the release process.

It also exposed the obvious weakness. Reviewing source in Files changed is possible on a phone; judging typography, navigation and image layout there is not pleasant.

Pull request 3: make the proposal visible

The third pull request added rendered previews and used its own preview as the end-to-end test. It also added topic indexes, wiki-style links, backlinks, related notes, static search and broken-link checking.

This changed the review object from “a Markdown file that should become a page” into “the page that will become public”. The prefixed preview forced URL handling, assets and navigation to work away from the site root, which caught a more realistic class of deployment errors than a local Markdown read-through.

Pull request 4: separate planning from publication

The editorial backlog contains roughly eighty candidate notes grouped into subject hubs and classified as ready from evidence, requiring reconstruction, or requiring a new experiment. It belongs in the private workshop, not on the public notebook.

Pull request 4 made that page render only when SITE_PREVIEW=true. Phil could review the backlog through the same phone-friendly machinery while the production build deliberately omitted /editorial/. The workflow had become useful for private editorial decisions as well as public articles.

Pull requests 5 and 6: make the articles defensible

The GCSE local-model benchmark and Sonoff firmware-rescue articles established the content discipline now used by default:

  • reconstruct against preserved project evidence rather than memory alone;
  • show an honest retrospective projectPeriod instead of pretending the article date is the project date;
  • add one explanatory visual by default, preferably a deterministic diagram or real artefact;
  • attach a small set of verified primary resources with a reason for each;
  • use wiki links to connect established concepts across the notebook;
  • verify both clean production and prefixed preview builds before opening the review gate.

Those rules were then captured in a reusable publishing skill. The important automation is therefore not only the YAML in GitHub Actions. It is the repeatable editorial procedure around evidence, privacy, validation, review and proof.

Details that did more work than expected

Several small choices made the workflow calmer.

Project time is not publication time

The front matter keeps date as publication metadata, but uses projectDate for ordering and projectPeriod for the reader-facing label. A reconstructed June project now sits in June even if Tiggy writes it in September. Approximate truth is better than precise-looking fiction.

Links form a lightweight knowledge layer

Topics generate index pages and related notes. A canonical wikiSlug lets [[wiki-style links]] resolve to a specific article, while other keywords fall back to their topic pages. Backlinks show which notes refer to the current one. This gives the notebook some wiki behaviour without adding a service or maintaining a separate graph.

The build rejects stale internal paths

Preview URLs live below a prefix while production lives at the root. A helper rewrites local URLs for both shapes, and the checker walks every emitted HTML file to verify local links and image sources exist. It is intentionally modest—it does not pretend to validate the whole web—but it catches the failures this repository can control.

Public previews need public-writing discipline

The private repository may contain evidence and planning that should never leave it. The rendered preview must contain only material safe for eventual publication. Internal addresses, credentials, household detail, security-sensitive topology and unnecessary identifiers are removed or generalised before deployment.

What “one tap” really bought us

The project did not eliminate work. A strong retrospective still requires evidence recovery, factual checking, editing, link verification, build inspection and judgement. What it eliminated was release ceremony and ambiguity.

There is one visible unit of change, one rendered place to review it, one explicit approval action, and a deterministic route from that approved commit to production. Drafts and editorial context stay private. The public site is static, searchable and free of trackers. Failed builds stop before publication, and successful jobs are followed by checks against the thing a reader can actually fetch.

That is the useful version of automation: not removing the human from the decision, but making the human decision the only manual step that remains.
