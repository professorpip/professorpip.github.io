A tiered model architecture for an OpenClaw agent

Project period · June–September 2026

Why one assistant ended up with cloud reasoning, a wake-on-demand GPU worker and a small local emergency model.

  • Agent Architecture
  • Local AI
  • Reliability
  • OpenClaw

In brief

  • No single model path met our quality, privacy, cost and resilience needs.
  • Cloud models remained the main reasoning tier.
  • A 16 GB GPU machine became a wake-on-demand local worker for bounded jobs.
  • A 16 GB Mac mini could run a much slower local Qwen profile when everything else was unavailable.
  • Health checks and explicit routing mattered more than automatic fallback alone.

Tiggy is a personal OpenClaw agent running on a 16 GB Mac mini. OpenClaw supplies the persistent session, tools, memory and routing around replaceable language models. “Run locally” therefore was not one architectural choice: by September 2026 the agent used three unequal model tiers with different jobs.

Architecture snapshot, September 2026: OpenClaw 2026.9.4 on macOS controlled the agent; cloud models handled the main reasoning path; an RTX 5060 Ti 16 GB machine served wake-on-demand local profiles; and the Mac mini retained a smaller emergency llama.cpp path.

Three unequal tiers

The primary tier uses cloud models for conversations, ambiguous planning and work where judgement matters. It is the most capable and the least dependent on home hardware, but requires an external service.

The second tier is a Ryzen desktop with a 16 GB NVIDIA GPU. Wake-on-LAN brings it up when a private, repeatable or compute-heavy job suits a local model. The server binds to localhost and is reached through an SSH tunnel, avoiding a bare model endpoint on the LAN. Months of testing produced separate profiles for reliable agent work, heavyweight review and long context.

The final tier lives on the Mac mini which hosts Tiggy. A low-bit Qwen3.8 27B experiment could answer at roughly 8 tokens/s, retrieve a needle from a 3,269-word prompt and stay below swap. That is not a pleasant main agent. It is enough for a terse emergency response or a bounded diagnostic when both cloud and Ryzen paths disappear.

Why routing beats substitution

These tiers are not interchangeable replicas. The local models miss exact contracts that cloud models handle; the emergency model is too slow for sprawling tool loops; the Ryzen can be asleep or booted into another operating system. Automatic failover without task awareness could turn a graceful outage into confidently poor work.

So the routing contract is conservative:

  1. test endpoint health, not merely process existence;
  2. send only tasks within the fallback model’s proven envelope;
  3. reduce context and tool surface as capability falls;
  4. fail closed on external writes and consequential control;
  5. report degraded mode rather than pretending nothing changed.

The resulting three-tier architecture

The tiered brain does not eliminate outages. It separates them. Cloud trouble need not erase local diagnostics; a sleeping GPU need not block ordinary chat; an overloaded emergency process must not survive forever after the main service recovers.

Resilience came from explicit roles, measured limits and boring health checks—not from putting three model names into a fallback list.
