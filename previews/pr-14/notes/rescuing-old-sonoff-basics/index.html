Rescuing old Sonoff Basics with Tasmota and ESPHome

Project period · June–July 2026

Two 1 MB ESP8266 switches survived a seven-year firmware gap, an OTA platform migration and two very different second lives.

  • Home Assistant
  • Esphome
  • Tasmota
  • Hardware Reuse
  • Automation

In brief

  • Two 1 MB Sonoff Basics were still on Tasmota 6.2.1.11 from 2018—and shared the same MQTT topic.
  • We backed them up and used six verified Tasmota stages to reach 15.4 lite safely.
  • A 338 KB ESPHome image then migrated over the air; disabling UART logging avoided a GPIO1/DHT11 conflict.
  • One snapped sensor wire redirected the devices into different jobs rather than invalidating the software.
  • The fan controller defaults off; the guarded server-recovery relay defaults on and requires explicit confirmation.

Two original Sonoff Basics resurfaced in June 2026 with DHT11 sensors, 1 MB flash and seven-year-old firmware. Uploading ESPHome directly would have ignored the supported firmware path, OTA space limits and the fact that these were mains-powered devices.

Inventory before upgrade

Both devices used the MQTT topic sonoff. If powered together, either could answer a command intended for the other. We therefore discovered them one at a time, downloaded configuration backups and assigned unique identities.

The broader lesson: inventory names, topics, pins and flash size before reconnecting old automation hardware.

The firmware ladder

The successful route was:

  1. 6.2.1.11 → 6.7.1 using the older sonoff.bin;
  2. 6.7.1 → 7.2.0 minimal;
  3. 7.2.0 minimal → 7.2.0 lite;
  4. 7.2.0 lite → 8.5.1 lite;
  5. 8.5.1 lite → 9.1.0 lite.gz;
  6. 9.1.0 → 15.4.0 release-lite.gz.

After each stage we waited for the device to restart and report the expected version. The final lite build used about 511 KB, leaving roughly 492 KB for the next OTA operation.

That ladder is historical, not universal. The reusable method is to follow current upgrade documentation, use suitably small builds and prove every restart.

Crossing to ESPHome

The compact ESPHome candidate used about 338 KB flash and 30 KB RAM:

  • relay GPIO12;
  • inverted pull-up button GPIO0;
  • inverted status LED GPIO13;
  • DHT11 data GPIO1;
  • serial logger disabled with baud_rate: 0.

GPIO1 is normally the ESP8266 transmit pin. Disabling UART logging stopped it competing with the DHT11. Both OTA migrations completed, and Home Assistant exposed the relay, button, temperature, humidity and firmware update without opening the mains enclosures.

Repurposing the two recovered switches

Weeks later, one DHT11 became unknown while its ESPHome node and relay remained healthy. Physical inspection found a snapped wire. The working sensor went to a garden-room fan; the other device became a pure relay.

The fan turns on above 26 °C and off below 25 °C, using hysteresis to avoid relay chatter. It logs real transitions and uses RESTORE_DEFAULT_OFF.

The second switch is a last-resort server-recovery path, not an everyday socket. It uses ALWAYS_ON, disables API-disconnect reboot behaviour and requires explicit confirmation for off, on or cycle operations. A supervised ten-second power-cycle test restored the server; the full stack took about seven minutes to return.

The same hardware needed opposite restore defaults because the consequences were different. That was the real result: safe reuse depends less on making a device clever than on matching guardrails to its job.
