Building a modular WebRTC voice gateway for two AI agents

Project period · September 2026

Mark 2, a shared WebRTC speech transport, lets one spoken wake word move the same microphone and speaker between two independently hosted agents.

  • Voice
  • Agent Architecture
  • WebRTC
  • Home Lab

In brief

  • Two independently hosted agents, Tiggy and Midge, previously each needed their own separate voice setup.
  • Mark 2 keeps one proven speech pipeline on the Mac mini and adds a swappable “agent adapter” behind it.
  • A spoken wake word, Operator, switches the live microphone/speaker session between agents without restarting anything.
  • Real accent variation broke the first parser; a narrow, command-scoped correction fixed it without touching normal conversation.
  • The older Mark 1 service was left untouched, so a regression in the new gateway could never take down the working voice interface.

Setup, September 2026: an M4 Mac mini running macOS 26.4.1, with Tiggy on OpenClaw 2026.9.4 and its local speech stack (WebRTC capture, VAD, ASR, TTS) on the same machine. Midge runs as a separate Hermes Agent in an Ubuntu VM, reached over SSH, not an exposed network port.

Tiggy already had a working local voice interface: browser microphone capture, echo cancellation, voice-activity detection, local speech recognition and local speech synthesis, all on the Mac mini. Separately, a second agent called Midge ran as an isolated worker, a Hermes Agent hosted in its own Ubuntu VM, reachable only through text over SSH. The obvious next question was whether the same microphone and speaker could be pointed at either agent on request. That meant no duplicated speech stack and no new network listener on the VM.

The setup and the problem

The proven speech transport used WebRTC for browser audio capture with built-in echo cancellation, plus a voice-activity detector to gate speech. A local ASR model and a local TTS model handled recognition and replies. All of that ran on the Mac mini and stayed as it was.

The engineering challenge was the layer underneath. One voice front end had to talk to two structurally different agents without either gaining access it shouldn’t have. A bug in the new switching logic also had to never take down the pipeline already working reliably for Tiggy.

Tiggy already lived on the same OpenClaw Gateway as the voice service, reachable through native session events with real-time interruption support. Midge, on a separate VM behind SSH, exposed a supported JSON-RPC protocol over that connection: session creation, prompt submission, streamed message deltas, message completion, and session interruption. It had no public network port of its own. The constraint was to use that existing protocol rather than open a new listener on the VM just for voice.

What we tried

Adapter contract, not model rewrite. Rather than teach the speech pipeline about two different agents directly, Mark 2 introduced a small adapter interface: connect, send text, receive streamed reply text, interrupt. Tiggy’s adapter used the OpenClaw Gateway’s native session and steering controls. Midge’s adapter opened a persistent SSH connection to the existing Hermes JSON-RPC gateway and spoke its documented methods. Neither adapter needed a new network-facing service.

A parallel, not a replacement. The new gateway ran as a second LaunchAgent on different ports, alongside the original working voice service, called Mark 1. If Mark 2 broke, Mark 1 kept working. Every regression test re-checked that Mark 1’s health endpoint and a full WebRTC round trip still passed after each Mark 2 change.

A spoken control channel. A small set of commands, gated by a wake word, let someone switch agents by voice without ordinary conversation being misread as a control instruction. The chosen wake word was Operator, with commands like “Operator, connect me to Tiggy,” “Operator, connect me to Midge,” “Operator, who am I connected to?” and “Operator, disconnect.”

Real speech broke the naive parser, twice. Local speech recognition on real British accents didn’t recognise “Midge” reliably. Logged transcripts included “connect meter image” and “connect meter tig” for the two agent names. A live run produced “Operator connect need to midget.” General fuzzy matching risked corrupting ordinary speech, so that wasn’t the fix. It was a narrow correction applied only once an Operator wake word and a connect-intent shape had already matched, mapping known misrecognitions to the two configured endpoints. Fourteen automated parser/router/queue tests, plus full WebRTC proofs of switching between agents with real recognised speech and streamed audio replies, passed after the fix.

Cleaning up connection state. An agent-switching voice UI has to fully release the old session on every disconnect: microphone, data channel, remote audio, peer connection. It must also ignore any late event from a retired session. Otherwise a stale reconnect could resurrect the wrong backend mid-conversation. Both browser and server side were made explicit about this: a new connection can never be silently overwritten by a callback belonging to an old one.

Making the speech safe to hear. An unrelated discovery during testing: a live agent’s raw text reply, with Markdown formatting, emoji, raw URLs, isn’t safe to feed directly to a text-to-speech engine. It will literally say “asterisk” or read out an emoji’s accessibility name. Mark 2’s fix has two layers. Each agent gets a short instruction to keep audio-mode replies in plain, brief sentences. A deterministic renderer also strips any remaining Markdown, URLs, HTML and emoji before the text reaches the speech synthesiser, so the safety doesn’t depend on the model obeying a prompt.

Result

Independent parser and router unit tests passed 14/14. End-to-end WebRTC proofs covered Operator switching a live session from Tiggy to Midge and back. They also covered a genuine Tiggy conversation with real recognised speech and streamed audio reply, and the same for Midge over its SSH JSON-RPC bridge. After a full test pass, both Mark 1 and Mark 2 health endpoints reported healthy with zero connected peers and no orphaned processes on either the Mac mini or the VM. The new gateway idled at roughly 627 MiB resident, a modest cost for a second full backend option.

What we would do next

Mark 2 became the accepted foundation for later voice work. Its transport, adapter pattern and Operator switching logic carried forward largely unchanged into the next phase, described in Mark 4’s product pivot. The open item is that a reliable spoken interface needs continued attention to accent and dialect variation in the wake-word and command parser. These fixes were reactive, not a general solution.
