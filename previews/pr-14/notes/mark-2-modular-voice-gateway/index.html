Building a modular WebRTC voice gateway for two AI agents

Project period · September 2026

Mark 2, a shared WebRTC speech transport, lets one spoken wake word move the same microphone and speaker between two independently hosted agents.

  • Voice
  • Agent Architecture
  • WebRTC
  • Home Lab

In brief

  • Two independently hosted agents, Tiggy and Midge, previously each needed their own separate voice setup.
  • This project, internally Mark 2, keeps one proven speech pipeline on the Mac mini and adds a swappable “agent adapter” behind it.
  • A spoken wake word, Operator, switches the live microphone/speaker session between agents without restarting anything.
  • Real accent variation broke the first parser; narrow, command-scoped correction fixed it without touching normal conversation.
  • The older Mark 1 service was left completely untouched, so a regression in the new gateway could never take down the working voice interface.

Setup, September 2026: an M4 Mac mini running macOS 26.4.1, with Tiggy running on OpenClaw 2026.9.4 and its local speech stack (WebRTC capture, VAD, local ASR and local TTS) on the same machine. Midge runs as a separate Hermes Agent in an Ubuntu VM, reached over SSH rather than any exposed network port.

Tiggy is an OpenClaw agent that had already earned a working local voice interface: browser microphone capture, echo cancellation, voice-activity detection, local speech recognition and local speech synthesis, all running on a Mac mini. Separately, a second agent called Midge ran as an isolated worker, a Hermes Agent hosted in its own Ubuntu VM, reachable only through text over SSH. The obvious next question was whether the same physical voice setup — the same microphone, the same speaker, the same “ears and mouth” — could be pointed at either agent on request, without duplicating the speech stack or exposing a new network listener on the VM.

The setup and the problem

The proven speech transport used WebRTC for browser audio capture with built-in acoustic echo cancellation, a voice-activity detector to gate speech, a local automatic speech recognition model, and a local text-to-speech model to generate replies. All of that ran on the Mac mini and stayed exactly as it was.

The engineering challenge was the layer underneath: how do you let one voice front end talk to two structurally different agents without either agent gaining access it should not have, and without a bug in the new switching logic ever being able to take down the speech pipeline that was already working reliably for Tiggy?

Tiggy already lived on the same OpenClaw Gateway as the voice service, so it could be reached through native session events with real-time interruption support. Midge, as a Hermes Agent, lived on a separate VM behind SSH, and its own agent runtime exposed a supported JSON-RPC protocol over that SSH connection — session creation, prompt submission, streamed message deltas, message completion and session interruption — but no public network port of its own. The design constraint was to use that existing protocol rather than opening a new listener on the VM just for voice.

What we tried

Adapter contract, not model rewrite. Rather than teach the speech pipeline about two different agents directly, Mark 2 introduced a small adapter interface: connect, send text, receive streamed reply text, interrupt. Tiggy’s adapter used the OpenClaw Gateway’s native session and steering controls. Midge’s adapter opened a persistent SSH connection to the existing Hermes JSON-RPC gateway and spoke its documented session.create / prompt.submit / message.delta / message.complete / session.interrupt methods. Neither adapter needed a new network-facing service.

A parallel, not a replacement. The new gateway ran as a second LaunchAgent on different ports, alongside the original working voice service, called Mark 1 in the project’s own language. If Mark 2 broke, Mark 1 kept working. Every regression test explicitly re-checked that Mark 1’s health endpoint and a full WebRTC round trip still passed after each Mark 2 change.

A spoken control channel. The obvious way to let someone switch agents by voice is a small set of commands gated by a wake word, so ordinary conversation is never misread as a control instruction. The chosen wake word was Operator, with commands such as “Operator, connect me to Tiggy,” “Operator, connect me to Midge,” “Operator, who am I connected to?” and “Operator, disconnect.”

Real speech broke the naive parser, twice. Local speech recognition on real British accents did not recognise “Midge” reliably. Logged transcripts included “connect meter image” and “connect meter tig” for the two agent names, and a later live run produced “Operator connect need to midget” and a version where the wake word was recognised as a separate fragment from “Connect me to the midge.” The fix was not a general fuzzy-matching layer, which risked corrupting ordinary speech; it was a narrow correction applied only once an Operator wake word and a connect-intent shape had already matched, mapping a small set of known misrecognitions to the two configured endpoints. Fourteen automated parser/router/queue tests, plus full WebRTC proofs of switching from Tiggy to Midge and back with real recognised speech and real streamed audio replies, passed after the fix.

Cleaning up connection state. An agent-switching voice UI has to fully release the old session — microphone, data channel, remote audio and peer connection — on every disconnect, and it has to ignore any late event that arrives from a session that has already been retired. Otherwise a stale reconnect could resurrect the wrong backend mid-conversation. Both the browser and the server side were made explicit about this: a new connection can never be silently overwritten by a callback belonging to an old one.

Making the speech safe to hear. An unrelated but important discovery during testing was that a live agent’s raw text reply — Markdown formatting, emoji, raw URLs — is not safe to feed directly to a text-to-speech engine; it will literally say “asterisk” or read out an emoji’s accessibility name. Mark 2 added a two-layer fix: each agent was given a short instruction to keep audio-mode replies in plain, brief spoken sentences, and a deterministic renderer strips any remaining Markdown, URLs, HTML and emoji immediately before the text reaches the speech synthesiser, so the safety property does not rely on the model obeying a prompt.

Result

Independent parser and router unit tests passed 14/14, and end-to-end WebRTC proofs covered: Operator successfully switching a live session from Tiggy to Midge and back; a genuine Tiggy conversation with real recognised speech and real streamed audio reply; and the same for Midge over its SSH JSON-RPC bridge. After a full test pass, both the Mark 1 and Mark 2 health endpoints reported healthy with zero connected peers and no orphaned processes on either the Mac mini or the VM.

Point-in-time memory measurement showed the new gateway idling at roughly 627 MiB resident, a modest cost for adding a second full backend option to an existing speech pipeline.

What we would do next

Mark 2 became the accepted foundation for later voice work rather than a one-off experiment: its transport, adapter pattern and Operator switching logic were carried forward largely unchanged into the next phase of the project, described separately in Mark 4’s product pivot. The one open item flagged at the time was that a genuinely reliable spoken interface needs continued attention to accent and dialect variation in the wake-word and command parser, since the fixes made here were reactive rather than a general solution.
