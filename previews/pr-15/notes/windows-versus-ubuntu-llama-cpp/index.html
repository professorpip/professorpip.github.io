Windows versus Ubuntu for local LLM inference on the same PC

Project period · August–September 2026

Dual-booting one Ryzen PC let us test the identical GGUF model on Windows and Ubuntu with the same GPU, and the operating system mattered more through VRAM headroom than raw token throughput.

  • Local AI
  • Benchmarking
  • Inference
  • Ryzen

In brief

  • The same Ryzen PC was dual-booted with Windows and a second Ubuntu install on its own drive, letting the same GPU run the exact same GGUF model file under each OS via a shared NTFS mount.
  • Raw decode speed without speculative decoding was almost identical: about 27.5–27.6 tokens/second on both operating systems for the same 27B model.
  • The real difference was VRAM headroom: the same 32K-context, MTP-enabled configuration left Windows only about 530 MiB of free VRAM, while Ubuntu’s identical setup left roughly three times that.
  • That headroom is what let Ubuntu run configurations Windows couldn’t sustain reliably: quantised KV cache plus speculative decoding at 32K context, delivering 47.8 tokens/second versus a 27.5 tokens/second baseline.
  • Lesson: for local LLM work on a single GPU, the OS choice showed up less in throughput and more in how close to the VRAM ceiling you’re forced to run.

Question

A Ryzen 9 3950X PC with 64 GB RAM and an RTX 5060 Ti 16 GB was already running local LLM experiments on Windows. Once a second NVMe drive was added and set up with Ubuntu Server, the obvious next question was practical rather than theoretical: for the same GPU and the same downloaded model file, does the operating system actually change anything that matters for local inference, or is llama.cpp on CUDA close enough to identical that OS choice is a non-issue?

Setup

Point-in-time context, September 2026: Ryzen 9 3950X, 64 GB RAM, RTX 5060 Ti 16 GB (NVIDIA driver 595.84, CUDA 13.1/13.2 depending on toolchain), one NVMe running Windows 11 and a second NVMe running Ubuntu Server. The Windows NTFS volume is mounted read/write under Ubuntu, so the exact same GGUF model files are usable from either OS without duplicate downloads.

The comparison used the same model both times: a 27B-parameter Qwen3.8 build quantised to IQ4_XS, about 14.25 GB on disk. Windows ran upstream llama.cpp build b10701; Ubuntu was built from source at a very similar upstream commit (build b10728), using CUDA toolkit 13.1.115 compiled locally with cmake/nvcc. Both used the same launch pattern: full GPU offload, Flash Attention on, reasoning off.

What we tried

Same model, same context, no speculative decoding. At 32K context with the default (unquantised) KV cache, both operating systems produced almost identical decode speed on short prompts: about 27.5–27.6 tokens/second either way. This was the first useful negative result: llama.cpp’s CUDA backend behaves the same across OS for the pure compute path, so raw throughput was never really the question.

Same model, same context, with speculative decoding (MTP). This is where the operating systems diverged. On Windows, the 32K single-slot configuration loaded at about 15,779 MiB used out of 16,311 MiB total — leaving only around 530 MiB of headroom. Adding native multi-token-prediction (MTP) speculative decoding at that context size was consistently tight, and smoke tests on Windows only reached the 45–53 tokens/second range on very short probes rather than a stable sustained figure.

On Ubuntu, the same 32K-context, MTP-enabled run with a quantised KV cache (q4_0 for both K and V) loaded at about 14,584 MiB used, leaving close to three times Windows’ headroom. A 300-token generation comparison at that setting measured 47.8 tokens/second with MTP versus 27.5 tokens/second without it — a clean, repeatable, nearly 74% uplift, made possible specifically because there was enough spare VRAM for the extra draft-token buffers that MTP needs.

Why the VRAM gap exists at all, as far as we could tell. Neither OS changed model size or context size; the difference tracked driver/runtime baseline VRAM reservation and background GPU consumers. Windows carries desktop compositor and driver overhead that a headless Ubuntu Server install does not, and that fixed overhead is what determined whether there was room left over for MTP’s extra allocation. This matches the pattern reported upstream: llama.cpp’s native MTP implementation reserves a separate CUDA compute arena, and tight VRAM configurations can fail to allocate it even when the base model fits comfortably without MTP.

Testing MTP depth as an independent variable. On Ubuntu, once there was enough headroom to experiment, sweeping the MTP draft depth found a clear sweet spot: depth 2 gave the best generation speed (about 45.6 tokens/second on a short chat prompt) with draft-token acceptance around 59%; depth 3 and depth 4 both regressed as acceptance rate fell, confirming that “more speculative tokens” is not automatically faster once acceptance drops below a useful threshold.

Result

Configuration OS Generation speed VRAM used / free
32K, no MTP Windows ~27.6 tok/s ~15,779 / ~530 MiB free
32K, no MTP Ubuntu ~27.5 tok/s ~15,252 / ~1,059 MiB free
32K, q4 KV, MTP depth 2 Windows 45–53 tok/s (short smoke only, unstable at full context) ~530 MiB free at baseline, tighter under MTP
32K, q4 KV, MTP depth 2 Ubuntu 47.8 tok/s (sustained, repeatable) ~14,584 / ~1,700+ MiB free

Raw compute throughput without speculative decoding was, for practical purposes, a tie between the two operating systems on this hardware. The meaningful difference was that Ubuntu’s lower fixed VRAM overhead created enough spare headroom to run configurations — quantised KV cache plus MTP speculative decoding at long context — that Windows could only run as short, less stable smoke tests rather than a dependable default profile.

What we would do next

The most direct follow-up is testing whether the same headroom advantage holds at even larger context windows (64K, 80K) where VRAM pressure becomes the binding constraint for every configuration, not just speculative decoding. It would also be worth isolating how much of Windows’ VRAM overhead comes from the desktop session specifically, by testing Windows in a headless/Server-style configuration rather than assuming the standard desktop install is representative of the ceiling. For now, the practical takeaway already shapes how this Ryzen PC gets used: Ubuntu is the default OS for serious local-model work on this hardware, and Windows is kept available for one-off tests and any tooling that specifically needs it.
