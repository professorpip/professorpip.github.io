Windows versus Ubuntu for llama.cpp on the same Ryzen PC

Project period · August-September 2026

Adding a second NVMe with Ubuntu let the same Ryzen GPU run llama.cpp from either OS off one shared model store, with dual-boot control mattering more than raw speed.

In brief

  • A second NVMe drive let a Windows gaming/LLM PC dual-boot into Ubuntu without touching the existing Windows install.
  • A persistent, boot-safe NTFS mount let both operating systems share one model file store, so nothing had to be downloaded twice.
  • Once builds and quantisation matched, llama.cpp performance was close between Windows and Ubuntu on the same GPU. The real win was safe dual-boot control, not raw speed.
  • Ubuntu-side wake-on-LAN after shutdown stayed unreliable despite several fixes, while Windows-side WoL worked cleanly.
  • A later DDR4 frequency bump helped CPU/MoE-heavy models modestly and did nothing for GPU-resident ones.

Question

The Ryzen 9 3950X / RTX 5060 Ti 16GB PC had been a Windows-only local-LLM box, using Windows llama.cpp builds against a growing Hugging Face model collection. Ubuntu Server went on a second NVMe to get a proper Linux platform without losing the existing Windows setup or its downloaded models.

The real question wasn’t which OS is faster in the abstract. It was whether the same GPU, the same model files, and the same day-to-day workflow could genuinely serve both operating systems, and what would change once that was true.

Setup

Windows 11 stayed on the original 2TB WD_BLACK SN850X NVMe, untouched. Ubuntu Server went on a separate NVMe with its own boot entry. Passwordless SSH with sudo was set up on Ubuntu, matching the existing Windows access. The GPU driver stack (NVIDIA 595.84, CUDA 13.1) and a current ggml-org/llama.cpp CUDA/Blackwell build were installed fresh on Ubuntu. One small patch was needed to CUDA’s math_functions.h, for rsqrt/rsqrtf declarations under glibc.

What we tried

Boot-safe, reversible dual-boot. Ubuntu was set as the persistent default boot OS, with the UEFI BootNext mechanism used for one-shot Windows boots. A normal reboot always returns to Ubuntu with no lasting BIOS change. Both operating systems stayed available without a boot-order fight whenever either was needed.

Sharing the model store instead of duplicating it. Windows hibernation and Fast Startup were disabled so the NTFS volume was always safe for external read/write access. Ubuntu got a persistent, UUID-keyed, boot-safe mount of the Windows C: drive at /mnt/windows. This exposed the existing Windows GGUF collection to Ubuntu directly, so quantisations already downloaded and tested on Windows became testable from Ubuntu’s newer build without another multi-gigabyte download.

A genuine like-for-like comparison. With the shared mount in place, the same previously-tested Windows GGUF ran directly from /mnt/windows under the Ubuntu llama.cpp build. Neither the model nor the build differed between the two sides. Historical Windows results and the fresh Ubuntu run became directly comparable: never re-download a model just to move operating systems.

Where the OS choice stopped mattering. Once quantisation, context size, KV-cache mode and build were held constant, llama.cpp inference numbers were close between Windows and Ubuntu on the same GPU. That was expected, since both drove the same CUDA stack on the same silicon. The interesting differences lived elsewhere: filesystem I/O and boot/power behaviour, not token generation.

Where it didn’t. A separate NVMe throughput test exposed a real filesystem gap. The faster raw drive (~3.61 GB/s) achieved only ~0.96 GB/s through the NTFS-3G/FUSE path under a real io_uring-heavy workload. A native ext4 drive doing the same job managed ~1.94 GB/s. NTFS-3G is fine for casually sharing already-loaded model files, but not for a serious I/O-bound Linux workload.

Power and wake behaviour diverged sharply. Windows-initiated shutdown-then-wake-on-LAN worked reliably. Ubuntu-initiated shutdown-then-WoL did not, even after enabling standby power, Netplan WoL configuration, a shutdown hook, PCIe wake, disabling Energy-Efficient Ethernet, and setting the BIOS “Restore AC Power Loss” option to Power On. This stayed an open, parked problem, later addressed with dedicated physical recovery hardware instead of a further OS-level fix.

A later memory tweak showed the two environments still have different bottlenecks. Increasing DDR4 from 2666 to 2933 MT/s produced no measurable change for GPU-resident models like Dirk (43.16 → 43.12 tok/s). It gave a modest, repeatable 5-6% uplift for the CPU/MoE-heavy Flash-Next Q2 profile (16.0 → 16.9 tok/s). “The OS doesn’t matter for speed” only held once a workload was safely inside VRAM; CPU-offloaded MoE work stayed sensitive to system memory bandwidth regardless of OS.

Result

The outcome wasn’t a performance verdict but an operating model: one Ryzen PC, two operating systems, one shared model library. A safe, reversible way to move between them meant no re-downloading and no risk to the working Windows install. Raw llama.cpp throughput on the GPU was close to identical across OSes once builds matched. The genuinely useful differences were in filesystem behaviour under a cross-OS mount and in power/wake reliability, not inference speed. Ubuntu-side WoL remained a known, unresolved gap at the end of this stage.

What we would do next

Ubuntu-shutdown wake-on-LAN wasn’t solved by OS-level configuration alone; a physical recovery path (servo button-presser plus JetKVM) was the eventual answer, covered in a later note. A further DDR4 timing pass, beyond the conservative frequency bump made here, was deferred pending a longer stability soak. The Windows/Ubuntu comparator itself is now reusable: any future GGUF or build change can be tested on both operating systems from the same shared model store without new downloads.
