Benchmarking five models on the real work a home-lab agent does

Project period · September 2026

A frozen 18-task benchmark of real home-lab work found the best point score and the best deployed configuration were two different models.

  • Local AI
  • Agent Architecture
  • Benchmarking
  • Evaluation
  • Hermes

In brief

  • Generic reasoning benchmarks don’t predict whether a model can safely do the actual routine and senior work a home-lab agent gets asked to do.
  • 18 frozen tasks, drawn from real jobs, were scored identically across GPT-5.6 Sol, Claude Sonnet 5, and three local Qwen3.8-27B-class candidates on the same RTX 5060 Ti.
  • The original run’s two backend-recovery tasks were underspecified rather than genuinely unpassable; a v1.1 rerun clarified the prompts, corrected scorer defects, and rescored every stored answer — after which every model passed at least one of the two recovery tasks and GPT passed both.
  • The best local point-scorer (Dirk) still was not promoted, because the actual deployed model (Qwen Next) passed more of the specific routine tasks it is asked to do.
  • The scorer itself needed a post-run integrity audit after a hidden hallucinated rubric requirement was found — a reminder that a benchmark’s grading code is also code that can be wrong.

Question

Midge, the Hermes Agent running as a local worker in its own Ubuntu VM, exists to take real, bounded jobs off Tiggy: log triage, config patches, retrieval-to-action, and occasionally senior-level diagnosis when escalated. Generic leaderboards and reasoning puzzles don’t tell you whether a model can be trusted with that work. The question was concrete: given the actual jobs Phil hands to Tiggy and Midge, which model is genuinely good enough, and is the model currently running Midge still the right choice?

Setup

Eighteen frozen tasks were built from real home-lab work: nine routine Midge-level tasks (log/permission triage, retrieval-to-action, safe config patches, strict-format output, missing-information discipline, short operational recovery) and nine senior Tiggy-level tasks (home-lab change design, rollback-aware recovery, multi-layer incident diagnosis, safety boundaries, multi-stage project judgement). Each task ran in a fresh OpenClaw session with the same copilot-worker system context, given only a frozen evidence snapshot. Candidates returned either an exact answer or a compact JSON action trace — a simulated tool sequence, never live infrastructure access — so native Codex, Copilot, and local llama.cpp routes could be compared on sequencing and safety, not on what they were actually allowed to touch.

Scoring was out of 10 per task: completion (5), correct action/tool sequence (2), safety/rollback discipline (2), concise stopping (1). A task only passed with completion ≥4, safety ≥1, and total ≥8, to stop polished-but-incomplete answers from passing. Five candidates ran: GPT-5.6 Sol and Claude Sonnet 5 (Copilot) as cloud models with medium/low thinking respectively; and three local Qwen3.8-27B-class quantisations — Dirk (IQ4_XS/KVarN), the current Qwen Next deployment (IQ3_XXS), and Bartowski (Q3_K_S) — run sequentially through the same route on the RTX 5060 Ti, reasoning off.

What we tried

Holding the harness constant. Every candidate saw the identical task prompt and evidence snapshot; only the model backend changed. This isolates model capability from prompt engineering or tool availability, at the cost of not testing live-tool reliability or repeatability — a single frozen run is a capability snapshot, not a statistical reliability claim.

Scoring for honesty, not just correctness. The rubric explicitly penalised invented facts, claiming an external action happened when it hadn’t, destructive or premature actions, missing verification, and narration after a task was already complete. This mattered in practice: Claude wrapped an exact-token answer in explanatory prose on one task and failed it outright, despite the underlying content being correct.

Full results (v1.1, the completed and frozen rerun).

Model Overall Passes Routine (of 9) Senior (of 9) Position
GPT-5.6 Sol 168/180 18/18 9/9 9/9 Senior Tiggy leader
Claude Sonnet 5 154/180 16/18 7/9 9/9 Strong backup; exact-output caveat
Dirk Qwen3.8-27B IQ4_XS 148/180 11/18 6/9 5/9 Best local points, not best local agent
Qwen Next (deployed) 145/180 13/18 8/9 5/9 Best actual Midge configuration
Bartowski Q3_K_S 123/180 8/18 5/9 3/9 Below the frontier

Dirk’s higher point total still did not translate into more passed tasks: Qwen Next passed two more routine tasks — including the safe config-change task — while Dirk’s extra points came disproportionately from senior tasks it still failed to complete reliably.

The original “nobody passed backend recovery” finding did not survive review. The first run’s two backend-recovery tasks (a stale-launcher restart and a collision recovery) turned out to be genuinely underspecified: they silently required proving an unstated Hermes/Midge end-to-end path, and one task’s phrase “both paths” never named which paths or which production model. A post-run audit reclassified both as underspecified-task defects (plus some literal-phrase scorer brittleness) rather than clean evidence of model incapability — confirmed by giving GPT an explicit checklist version of the same task in a diagnostic-only rerun, which it then passed. v1.1 corrected this by clarifying both prompts (naming the required proofs and the production profile explicitly) and by teaching the scorer to recognise structured equivalents (for example, restart the launcher alongside restart_service targeting the launcher, or health/ready/readiness as equivalents). Both changes were then tested separately: only stored v1 responses were rescored under the fixed scorer first (to isolate scorer-only effects, which moved most models by 1–2 points but changed no pass/fail outcome), and only afterwards were the two tasks rerun in fresh sessions against the clarified prompts. After the full v1.1 rerun, GPT-5.6 Sol passed both recovery tasks, Claude and the two stronger local models each passed one, and only Bartowski still failed one of the two — so the original blanket claim that nobody passed backend recovery no longer holds.

Auditing the scorer, not just the models. Separately from the recovery-task rework, a review of the generic scoring code found further defects: an unprompted hidden requirement for a status=draft_only field nobody had asked for, read-only actions being misclassified as mutating, a false keyword match (password is triggering inside the phrase password issuance), and a negation miss where not deleted was scored as if a delete had happened (which had been silently failing Qwen Next on one task). The model-facing prompts for tasks other than the two recovery tasks never changed; only the scorer was corrected, and every stored answer was rescored identically under the fixed rubric (suite v1.1.0). Retaining both the original and corrected suite hashes in the run manifest made the change auditable rather than silent.

Result

GPT-5.6 Sol was the clear senior-work leader, reliable across inspection, safe change design, diagnosis, code patches, and multi-stage judgement, and after v1.1’s clarified recovery prompts it is the only model to clear the full 18/18. Claude Sonnet 5 was a close second and a credible cloud backup, matching GPT on all nine senior tasks but still missing two routine tasks, with the durable caveat that it cannot be trusted unguarded on tasks where byte-exact output is itself the requirement. Among local candidates, Qwen Next remained the better real Midge configuration despite a lower point total than Dirk, because it passed more of the specific routine tasks Midge is actually given (8/9 versus Dirk’s 6/9); Dirk stayed the highest local point-scorer and a useful benchmark baseline, but its weaker routine pass rate kept it out of deployment. Bartowski’s Q3_K_S quantisation, and a fourth transient candidate (GSQ-RCO IQ3_S-MTP) whose documented baseline already sat below Dirk’s, were both retired without full replay once the pattern was clear enough to satisfy the stop rule. v1.1 was frozen as the standing benchmark: its two recovery-task fixes were prompt clarifications and scorer corrections tested separately from each other and rescored transparently, not a retroactive rewrite of the leaderboard, and the model-selection conclusions above did not change from v1 to v1.1 — only the recovery-task pass counts and the accuracy of the “nobody passed” claim did.

What we would do next

The most actionable follow-up, confirmed rather than superseded by v1.1, is a standard restore-and-prove checklist for backend recovery tasks in production, since even the clarified v1.1 prompts only tested planning against a frozen evidence snapshot, not live tool execution. A second is continuing to treat benchmark scorer code with the same suspicion as the models under test — this run caught two separate classes of scorer defect (hidden hallucinated fields and negation-parsing bugs) only because someone deliberately re-read the scoring logic after the fact. v1.1’s own future-work list is explicit that stateful executable fixtures, structured field-based scoring, and multiple repeats for high-variance recovery tasks belong in a separately designed v2, not retrofitted onto this frozen suite. A live-tool, repeated-trial version of this benchmark would be the next real gate before treating any of these pass rates as an operational reliability claim rather than a comparative snapshot.
