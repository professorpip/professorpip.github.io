Benchmarking real assistant work instead of reasoning puzzles

Project period · September 2026

A frozen 18-task benchmark of the actual jobs Phil gives his assistants found that the best local model and the best operational agent configuration are not the same thing.

  • Agent Architecture
  • Evaluation
  • Hermes
  • Local AI

In brief

  • Generic reasoning puzzles don’t predict how well a model does the actual jobs handed to a home assistant, so this benchmark uses 18 frozen, real work-style tasks instead.
  • Every candidate — two cloud models and three local llama.cpp builds — ran the identical tasks in a fresh session with a simulated action trace, never live infrastructure.
  • GPT-5.6 Sol led on senior-level work; Claude Sonnet 5 was a close but less trustworthy backup; and, critically, the model with the best raw score was not the best actual configuration for Midge’s day job.
  • Qwen Next, the model already running Midge, beat a supposedly stronger local model on the routine tasks that make up most of Midge’s real workload.
  • Lesson: benchmark score and operational recommendation are two different questions, and conflating them nearly demoted a working setup.

Setup, September 2026: an M4 Mac mini running macOS 26.4.1, hosting Tiggy on OpenClaw 2026.9.4. Midge runs separately as a Hermes Agent in an Ubuntu VM. The benchmark itself ran as a scripted OpenClaw harness driving fresh sessions per task, with local candidates served from a Ryzen PC running Ubuntu with an RTX 5060 Ti 16 GB GPU.

Question

Public agent benchmarks lean on generic reasoning or coding puzzles. None of them tell you whether a given model is good at the specific, unglamorous work an assistant actually does: reading a log, reconciling a device list, making a safe config edit, or knowing when to stop and say a recovery still needs proof. Two practical questions needed answering: which model is the best fit for Midge’s routine day-to-day work, and which model should take over when a task needs senior-level judgement that Midge shouldn’t attempt alone?

Setup

The benchmark suite is a fixed set of 18 tasks split into two tiers: nine routine tasks resembling Midge’s actual daily load (log triage, retrieval-to-action, safe config patches, strict output formats, missing-information discipline, short recovery), and nine senior-tier tasks resembling escalations Tiggy would normally handle (home-lab change design, rollback-aware recovery, multi-layer incident diagnosis, safety boundaries, multi-stage judgement calls).

Each task ships with a frozen evidence snapshot. A candidate model gets only the task prompt and evidence, and must return either an exact answer or a compact JSON action trace — a simulated tool sequence, not a live command. This keeps sequencing and safety comparable across very different backends (native cloud APIs and local llama.cpp) without ever giving a benchmark candidate a real shell, a real message queue, or a real host to touch.

Scoring is out of 10 per task: 5 for completion, 2 for correct action/tool sequencing, 2 for safety and rollback discipline, and 1 for stopping concisely once the task is actually done. A task only counts as passed if completion is at least 4/5, safety is non-zero, and the total reaches at least 8/10 — a deliberately strict gate meant to stop a polished-sounding but incomplete answer from passing.

Five candidates ran the full suite: GPT-5.6 Sol and Claude Sonnet 5 as cloud references, and three local llama.cpp builds on the Ryzen PC’s RTX 5060 Ti — Qwen3.8 Flash Next (Midge’s actual current model), a Qwen3.8-27B build nicknamed “Dirk” (the strongest all-round local baseline from earlier local-model testing), and a lower-quantisation Qwen3.8-27B variant as a lower bound.

What we tried

Running every candidate through the same evidence, cold. Each of the 18 tasks ran in its own fresh OpenClaw session using the same system context a real copilot-worker session would get, so no candidate could see another’s transcript or accumulate context across tasks.

Scoring audit before publishing a verdict. After all runs completed, the scoring rubric itself went through one semantic audit pass: an accidentally over-strict hidden requirement was removed, read-only or proposal-style actions were correctly reclassified as non-mutating, and a couple of false-positive keyword matches (a benign phrase that happened to contain the word “password”) were fixed. Every stored response was then rescored under the corrected rubric rather than re-run, keeping the raw model outputs untouched while fixing the rubric that judged them.

Separating “best score” from “best configuration.” The clearest finding did not come from the top of the leaderboard. Dirk, the stronger general-purpose local model by total points, actually lost two more routine tasks than Qwen Next — including the safe-config-change task that is a staple of Midge’s real job — despite scoring more points overall on senior-tier tasks Midge doesn’t actually get asked to do. Total score rewarded broad capability; the routine-task breakdown told the operationally relevant story.

Result

Model Overall Passes (18) Verdict
GPT-5.6 Sol 164/180 16 Senior-tier leader; two misses were both unproven recovery claims
Claude Sonnet 5 149/180 15 Strong backup; failed the byte-exact output task
Dirk (Qwen3.8-27B, local) 142/180 10 Best local point total, but weak on routine change/recovery
Qwen Next (Midge’s current model) 135/180 11 Fewer total points than Dirk, but wins on the routine tasks Midge actually faces
Lower-quant Qwen3.8-27B 120/180 7 Below the frontier on every category

No model, cloud or local, passed either end-to-end backend-recovery task cleanly: both GPT-5.6 Sol and Claude Sonnet 5 restored the target service conceptually but stopped short of proving the real recovery path, a useful reminder that “the service is listening again” is not the same claim as “the intended recovery actually happened.” A fixed recovery-and-proof checklist would close that gap for senior work regardless of which model runs it.

The operational recommendation split cleanly by tier: GPT-5.6 Sol for senior escalations where Midge should hand off, Claude Sonnet 5 as its supervised backup, and Qwen Next — not the higher-scoring Dirk — as Midge’s actual day-to-day model, because it passed more of the routine tasks that make up Midge’s real workload and already has the working integration.

What we would do next

The most durable lesson is procedural: always report both the raw benchmark leaderboard and a separate operational recommendation, because they answered different questions here and picking the wrong one would have meant swapping a working assistant model for a benchmark-flattering one that was actually worse at its job. The unresolved gap is backend-recovery proof: even the strongest models need an explicit checklist that verifies the real path, not just an endpoint responding, before that class of task can be trusted unsupervised.
