Why fitting in VRAM beat having more parameters

Project period · August–September 2026

Dense, MoE and hybrid-offload experiments showed why memory placement mattered more than the parameter number on the model card.

  • Local AI
  • Inference
  • Hardware
  • Optimisation

In brief

  • Parameter count did not tell us how a local model would feel in use.
  • A model wholly resident on the GPU was usually simpler and more predictable than a larger model spilling across PCIe.
  • MoE reduced active computation, but inactive experts still had to live somewhere.
  • Quantisation, KV cache and context length competed for the same 16 GB budget.
  • Our sweet spot was the best verified behaviour with deliberate headroom, not the largest model that barely loaded.

Model cards encourage a simple comparison: more parameters should mean more capability. A single 16 GB GPU turned that into a placement problem.

Test platform, August–September 2026: AMD Ryzen 9 3950X, 64 GB system RAM, PCIe-attached NVIDIA GeForce RTX 5060 Ti with 16 GB VRAM, and llama.cpp-family runtimes. Results below depend on quantisation, context length, KV-cache format and offload policy—not parameter count alone.

Dense and MoE are different bargains

A dense model uses all its weights for each token. A mixture-of-experts model activates only part of a larger network, so compute can be modest even when the total checkpoint is huge. The catch is storage: experts not currently active still need VRAM, system RAM or a trip across PCIe.

That produced counter-intuitive results in our shootout. A 30B-class MoE coding model generated above 120 tokens/s while a 26B Gemma MoE, loaded within a few hundred megabytes of the card limit, managed about 22–24. Architecture, quantisation and runtime support mattered as much as the headline size.

Context consumes VRAM too

Weights were not the whole budget. Longer context enlarged the KV cache; speculative decoding added draft state; expert caching traded RAM traffic for VRAM; the desktop and CUDA runtime needed space too.

One 80K Qwen3.8 profile worked with about 370 MiB free. It was technically successful and operationally brittle. A lower-bit profile left roughly 3.2 GiB at the same context and ran faster, but sacrificed some quality. At 96K, another tuned 27B quant used about 13.75 GB and passed five retrieval probes. That was a healthier engineering result than squeezing in a larger checkpoint and hoping traffic never spiked.

Offload experiments reinforced the point. FreeToken measured roughly 42.8 GB/s CPU memory bandwidth and 14.1 GB/s host-to-device PCIe bandwidth on the Ryzen box. A cache miss therefore crossed a link far slower than local GPU memory. The runtime was interesting, but its first agent smoke test scored 0/5 clean and exposed template, schema and context limits. Clever placement could not compensate for unreliable behaviour.

The rule we kept

For an always-available local worker, choose the smallest profile that passes the real acceptance gates and leaves enough memory for its intended context. Treat CPU spill as a deliberate trade, not free capacity. Measure ready-state and peak VRAM, not just file size.

The largest runnable model is a demo. The best-fitting verified model is infrastructure.
