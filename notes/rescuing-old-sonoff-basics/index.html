Rescuing old Sonoff Basics with Tasmota and ESPHome

Project period · June–July 2026

Two 1 MB ESP8266 switches survived a seven-year firmware gap, an OTA platform migration and two very different second lives.

  • Home Assistant
  • Esphome
  • Tasmota
  • Hardware Reuse
  • Automation

The two small white switches had been doing unremarkable jobs for years. Inside each was an original Sonoff Basic: an ESP8266, a relay, a button and just 1 MB of flash. Both had also been modified with a DHT11 temperature and humidity sensor.

When we rediscovered them on the network in June 2026, their firmware dated from 2018. They were still running Sonoff-Tasmota 6.2.1.11 while current Tasmota was on version 15.

The tempting plan was “upload ESPHome and see what happens”. The better plan was to treat the old firmware, tiny flash and mains-powered hardware with some respect.

First, identify what was actually there

The devices appeared one at a time as old Tasmota web interfaces. Each reported the same basic hardware and firmware constraints:

  • original Sonoff Basic module;
  • ESP8266 with 1 MB flash;
  • Tasmota 6.2.1.11;
  • relay, button and status LED;
  • an added DHT11 sensor;
  • MQTT configured against the home broker.

There was an immediate trap: both devices used the MQTT topic sonoff. Powering them simultaneously in that state could make one device respond to commands intended for the other. We therefore kept discovery controlled, downloaded configuration backups and gave the devices unique identities before treating them as a pair.

That small detail became the first reusable lesson. Old home-automation devices often contain assumptions from a time when they were installed one at a time. Discovery is not merely finding an IP address; it is checking names, topics, pins, flash size and anything else that may collide when the device rejoins a modern system.

Why the firmware ladder mattered

Jumping directly from a 2018 Tasmota image to a current one is not a supported upgrade strategy. File layout, settings storage and minimum compatible versions changed across the intervening releases. A full modern build can also be too large to leave enough free flash for the OTA process itself.

The successful route for both devices was:

  1. 6.2.1.11 → 6.7.1 using the older sonoff.bin image;
  2. 6.7.1 → 7.2.0 minimal;
  3. 7.2.0 minimal → 7.2.0 lite;
  4. 7.2.0 lite → 8.5.1 lite;
  5. 8.5.1 lite → 9.1.0 lite.gz;
  6. 9.1.0 → 15.4.0 release-lite.gz.

After every step we waited for the device to restart, reappear and report the expected version before continuing. The final lite build occupied about 511 KB, leaving roughly 492 KB of program space—comfortable enough to perform the next OTA migration without opening the mains enclosure.

The exact ladder is historical, not a universal recipe. Someone repeating this should follow Tasmota’s current upgrade documentation for their own starting release and hardware. The durable method is: identify the supported intermediate versions, use a suitably small build, and prove each restart before taking the next step.

Crossing from Tasmota to ESPHome

Once both devices were on a current Tasmota release, its firmware upload page could accept a compact ESPHome binary.

The first candidate compiled for ESPHome’s esp01_1m board at approximately 338 KB of flash and 30 KB of RAM. Its hardware mapping was deliberately small:

  • relay on GPIO12;
  • physical button on GPIO0 with inverted pull-up;
  • inverted status LED on GPIO13;
  • DHT11 data on GPIO1;
  • serial logger disabled with baud_rate: 0.

That final line was essential. GPIO1 is normally the ESP8266 transmit pin. Leaving serial logging enabled while asking the DHT11 to use the same pin creates two components fighting over one wire. Disabling UART logging preserved the custom sensor connection.

The first OTA upload completed, the node appeared in ESPHome, and Home Assistant exposed the relay, button, temperature, humidity and firmware-update entities. We then repeated the proven route on the second switch.

No serial adapter or open case was required. That reduced inconvenience, but more importantly avoided unnecessary contact with a mains-voltage device. OTA did not remove all risk—a failed flash could still have required physical recovery—but it kept the normal migration on the low-voltage side of the problem.

One apparent software failure was a wire

Weeks later, one DHT11 stopped returning useful values. The ESPHome node and relay were still reachable, while temperature and humidity became unknown.

It would have been easy to blame the unusual GPIO choice, the firmware migration or Home Assistant. Physical inspection found the simpler answer: a DHT11 wire had snapped.

That failure changed the design rather than invalidating it. The switch with the broken sensor became a pure relay device; the one with a working sensor went where temperature control was useful. “Check the wire” is not glamorous debugging advice, but it prevented a working software stack from being dismantled.

Second life one: a garden-room fan controller

The working sensor-and-relay device now controls a fan in the garden room. Home Assistant turns it on above 26 °C and off below 25 °C.

The one-degree gap is hysteresis. Without it, small fluctuations around a single threshold could make the relay chatter on and off. The automation also records a logbook message only when it performs a real transition, including the triggering temperature, so later investigation can distinguish heat-driven operation from a restart or temporary availability event.

Its relay uses RESTORE_DEFAULT_OFF: after an uncertain restart, an unattended fan should not assume it must run.

Second life two: guarded server recovery

The device with the broken DHT wire now sits in the power path of a home server. That sounds alarming because it can be alarming.

It is not an everyday remote-control socket. It is a last-resort recovery path for a machine that is genuinely unreachable and cannot be recovered through its normal interface. Its ESPHome configuration therefore makes different choices:

  • relay restore mode is ALWAYS_ON;
  • API disconnects do not trigger an automatic reboot;
  • ordinary status reads are allowed without changing power;
  • off, on and cycle operations require an explicit confirmation phrase;
  • recovery procedure checks that storage activity has been stopped or ruled out first.

We performed one supervised test after stopping the storage array. The relay cut power for ten seconds, restored it, and the server returned through BIOS, USB boot, networking and service startup. Network access began returning after a few minutes; the complete stack took about seven minutes.

The interesting result was not that a smart switch could remove power. It was that a cheap recycled relay could become a useful recovery layer only after its defaults, guardrails and verification were designed around the consequence of failure.

What the rescue taught us

The project started as firmware archaeology and ended with two useful devices that no longer resemble each other operationally.

The transferable lessons were straightforward:

  • inventory identities and shared MQTT topics before reconnecting old devices together;
  • respect documented intermediate upgrades across a long firmware gap;
  • build for the actual flash constraint rather than the nominal platform;
  • treat GPIO and UART assignments as physical resources, not just YAML;
  • diagnose hardware and software separately;
  • choose restore behaviour from the appliance’s failure mode;
  • put stronger confirmation and verification around actions with larger consequences.

Neither Sonoff became clever. One became a modest temperature controller; the other became a deliberately awkward emergency switch. The value came from making their behaviour legible, local and appropriate to the jobs they actually perform.
