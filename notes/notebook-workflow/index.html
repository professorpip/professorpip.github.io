Building a one-tap lab notebook

Project period · September 2026

How a private Markdown workshop, phone-friendly rendered previews and a separate public output repository turned one merge into a controlled publication.

  • Publishing
  • Github
  • Automation
  • Eleventy
  • Agent Architecture

In brief

  • Drafts, evidence and editorial planning stay in a private source repository; only generated files enter the public site repository.
  • Every pull request gets an unlisted, noindex rendered preview for phone review.
  • Merging that exact pull request is the human publication decision.
  • GitHub Actions rebuilds the approved source, publishes it through GitHub Pages and removes the closed preview.
  • Six completed pull requests and four live articles proved the loop before this write-up.

“One tap” describes the release, not the writing. A useful note still needs evidence, editing and checks.

Why two repositories?

A hosted CMS would add another account, database and maintenance job. A public source repository would expose drafts, editorial planning and revision history. GitHub Free could not publish Pages directly from the private source repository.

We split the system:

  1. The private repository holds Markdown, templates, evidence-led revisions, automation and the editorial backlog.
  2. The public repository holds only generated HTML, CSS, images and the Pagefind search index.

The private repository’s workflow has a deploy key that can write to the public one. Access does not flow back the other way. This keeps the workshop private while leaving the finished site cheap and static.

The working loop

Drafting is deliberately three-pass: write the full evidence-backed version; challenge every paragraph, sentence and word until only useful detail remains; then add no more than five bullets that give a time-poor reader the whole gist.

For each article:

  1. Tiggy reconstructs the project from preserved artefacts, using memory and transcripts only to locate evidence. Private operational details are removed or generalised.
  2. The article goes onto its own branch. A production-shaped build and a prefixed preview build both run Eleventy, Pagefind and the internal link-and-image checker.
  3. A pull request repeats the preview checks in GitHub Actions, publishes generated files beneath /previews/pr-N/, and comments the URL.
  4. Phil reviews that rendered page on his phone. Requested edits repeat the same loop.
  5. Merging the approved PR triggers a fresh production build and writes the result to the public Pages repository.
  6. We fetch the live article and assets. Closing the PR also removes its preview, which should then return 404.

Preview pages are public but unlisted and carry noindex, nofollow. That is useful review plumbing, not access control, so sensitive material never enters a preview.

An article can be draft: false on its branch without appearing in production: it is ready within the proposal, but production still comes only from main. The merge remains the explicit human gate.

We built it by using it

The repository history shows the useful progression.

  • PRs 1 and 2 proved the basic loop. The first articles—giving Tiggy a live voice and what Tiggy is—were reviewed through GitHub and published by merging. It worked, but reviewing Markdown under Files changed was a poor way to judge a page on a phone.
  • PR 3 added rendered previews. It used its own preview as the first end-to-end test, while also adding topic pages, wiki links, backlinks, related notes, Pagefind search and broken-link checks.
  • PR 4 proved private planning. The roughly eighty-item editorial backlog renders only when SITE_PREVIEW=true; production deliberately omits /editorial/.
  • PRs 5 and 6 tightened the editorial method. The GCSE benchmark and Sonoff rescue notes were reconstructed from project evidence, given honest project periods, supported by verified primary resources and limited to useful visuals. Those rules were then captured in a reusable publishing skill.

The first two PRs tested publication. The next four tested the publishing system itself.

Small choices that mattered

  • Project time and publication time are separate. projectDate controls ordering; projectPeriod is shown to readers; date remains publication metadata.
  • Wiki links stay lightweight. A canonical wikiSlug points to an article; other keywords fall back to topic pages. No graph database is involved.
  • Preview paths are real test cases. Running beneath /previews/pr-N/ catches asset and navigation mistakes hidden by root-only local builds.
  • A green source Action is not publication proof. The public repository has its own Pages deployment, so the final check is the URL a reader can fetch.

At this checkpoint the workflow had published four articles through six completed PRs, cleaned up their previews and kept the editorial backlog out of production.

The result is deliberately boring infrastructure: Markdown, Git, static files and one human decision. That is the good kind of automation.
